# 2026-08-29 — lineup-engine

规则与名单第一次在一起用：给一支队排出合法阵容。也是第一个每组都由独立评审
subagent 打分的 change —— 六组里有三次 BLOCK，全部是真问题。

## 完成内容

十三个 commit（`d99a508..5e8e1e9`），七个任务组。受评六组的分数：
99 / 99 / 99 / 98.4 / 99 / 96.4（阈值前四组 80，后两组 70）。

- **约束判定**（`app/lineups/rules.py`）：五条约束的合取，全程 `Decimal`。
  cap、buffer 额度、差距上限、高 UTR 阈值全部来自 `competition-rules` 的数据。
- **分支限界搜索**（`search.py`）：精确穷举，不用启发式 —— 报告的上限必须真的是
  上限。线序按合法搭档数从少到多（女双最少），以「剩余各线最强搭档之和」剪枝。
  候选按**上场十人的集合**去重。
- **只读端点** `GET /api/seasons/{year}/divisions/{code}/teams/{code}/lineups`，
  锁定与排除走可重复 query。没有新增任何写方法。
- **排阵页** `/[season]/[division]/lineup/[code]`：原生 GET 表单，锁定与排除只存在于
  URL；结果先给两个上限、差值与达到上限的十人组合数。
- **三种非正常状态**各有面板：无解（指名线位）、截断、外援未校验。第四种是
  「这条锁定本身不合法」—— 锁定会跳过逐线筛选，不单独报就会被读成「你的名单
  排不出来」。
- **侧栏**「分析」拆成「阵容」（真链接）与「对手对比」（保留未开放）。

真实数据实测：2025 全部 24 支球队各搜一次，全部返回完整结果、0 截断，
开发机最坏 0.09s。比 design 里记的 1.61s 快很多，原因是 2025 两组 Buffer 都是
0.00，可行空间小得多；2026 开了 Buffer 会明显变慢。**Render 免费实例上的真实
耗时还没测过**，节点预算是否合适要等部署后再复核 —— 开发机的数字不能代表它。

## 三次 BLOCK

评审 subagent 拿的是干净上下文，只看契约、spec 和 diff。三次都不是误报：

1. **group 2**：锁定的搭档完全绕过逐线合法性过滤。任务描述里本来就写着要校验，
   我在没实现、没测试的情况下打了勾，第一次 PASS 是虚的，撤回重做。
2. **group 6 第一次**：`lineup/` 两条路由没有自己的 `error.tsx`。取数一失败就冒泡到
   根 `error.tsx`，把侧栏一起清空 —— 契约里明写「侧栏 MUST 仍然渲染」。
   补完之后把 `BACKEND_URL` 指到没人监听的端口实测，侧栏确实还在。
3. **group 6 第二次**：排阵页有锁定时会跑两次整解（一次带约束、一次不带，用来算
   锁定的代价），当时是串行 `await`。冷启动的免费实例上叠加会接近函数超时，
   而两者互不依赖，改成 `Promise.all`。

第三次评审顺带发现 `getDivisionRules` 返回 null 时没有 `notFound()`，会渲染一个
没有任何 cap 的半截页面 —— 一套「看起来校验过」的阵容，其实什么都没校验。

## 交付后的三件事

- **锁定面板从 420 加宽到 520**：排除标签一人一个，26 人名单在 420 宽下要占十行，
  把面板顶过 640px 高的窗口，于是面板自己出滚动条而页面不滚。宽度是从候选卡那边
  匀过来的：过了约 460，金组的卡就会折到第三行，460 到 520 之间躲不掉这个代价，
  所以取余量最大的 520。
- **姓名显示成「姓 空格 名」**：两半来自组委会总表的 Last Name / First Name 两栏，
  之前直接拼在一起，真实名单上读作 `GuanpengChen` —— 不是任何人的名字。抽成
  `lib/name.ts` 一个 helper，四处显示统一走它。总表里少数几行两栏是填反的
  （`Guanpeng | Chen`），那是录入问题，显示逻辑修不了：中英混排的名单里没有办法
  可靠判断哪一半是姓。
- **赛季切换器看不清**：药丸底色用了 `bg-background`，那是浅色内容区的页面底色，
  配近白标签只有 **1.05:1**。侧栏是有自己配色的外壳，新加 `--color-sidebar-well`
  (#14130f，视觉稿本来的值)，改后 16.07:1。用户截图报上来的。
