## 四次 BLOCK，两次是迟到的

评审 subagent 拿干净上下文，四次拦下来的都不是误报：

1. **group 1**：`SeasonLock.locked_at` 对着 NOT NULL 列发显式 NULL，锁赛季必抛异常。
   模型要写 `server_default` 才会让数据库自己盖时间戳。
2. **group 6**：登录限速按 `x-forwarded-for` 第一段计数 —— 那是调用方能写的，轮换即
   绕过。改成可信 header + 一个 header 影响不到的全局配额。
3. **group 8**：未裁决队列按「数值大小」推断两个候选来自哪份总表。真实数据里较大值
   时而在金组（Chen Yilun 6.98）时而在银组（Zong Qingqing 6.38）——**那一列对一半的行
   说了反话**，而裁决恰恰要靠它。补了来源列，来源跟着值走。
4. **group 5 与 group 8 各有一次「迟到的 code review」**：评审已经返回 PASS（甚至打了
   100），它内部调的 code-review 子代理才把结果报上来，两次都带着真实的 HIGH ——
   合并的赛季锁范围过宽（会拒掉「老赛季关掉后才发现重复」这个主要用例）、
   以及 `tsc` 7 个错加合并后来源标签变陈旧。**PASS 不等于评审结束**，这条进了 pitfalls。

第 4 条里的 `tsc` 那个尤其值得记：`npm run test` 用 esbuild，只转译不校验类型，所以
前端 224 个测试全绿而 `next build` 会红。`npx tsc --noEmit` 已经单列成一条验证项。

## 本机工具链

`uv run` 现在连 venv 里的 python 都被 Application Control 拦（`os error 4551`，
`uv trampoline failed to spawn`），跟之前 uvicorn.exe 那条同类，只是范围扩大了。绕法是
用系统 python 自己建的 venv：`python -m venv backend/.venv-std`，那份 python.exe 是签名
解释器的副本，能跑。此后 pytest / uvicorn / seed / migrate 全走它。`pyproject.toml` 与
CI 仍以 uv 为准，这只是本机绕行。

同一天还发现新表会跟着 pytest 的 TRUNCATE **级联**消失（外键指向 `seasons` 与 `teams`），
留下一堆没有赛季记录的孤儿 `players`；恢复要先补种、再清空 players、最后重跑迁移 ——
只重跑迁移不会修好，因为它按姓名匹配到孤儿、判定为「已存在」。
