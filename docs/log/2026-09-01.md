## lineup-infeasibility-detail（无解诊断：为什么这条线凑不出）

opsx 四阶段走完并归档（`2026-09-01-lineup-infeasibility-detail`）。起因是负责人提的三条
阵容增强里最自包含的一条（A）：某条线撞到无解时，界面只说「{线}没有任何合法搭档」，不说
为什么、也不说是不是自己排除/锁走造成的。B（保存过滤）、C（保存阵容+失效标记）留作后续
单列。commit `5490b16`(req) → `4e24e59`(propose) → `aa87665`(后端) → `286cfcd`(前端) →
`e4f1c03`(验证) → `9d95f45`(eval) push master，自动部署 Vercel + Render。

### 做了什么

后端 `search()` 在 `infeasible_line` 旁多返回结构化 `infeasibility`（`line` + `reasons[]`）：
四类客观原因——性别人手不足 / 都超 cap / 都超搭档差距 / 资格线限制，多因并存全列。可直接
读出时归因到用户动作（被排除、锁进别线），点名 + 去向；`over_cap`/`over_gap`/`eligibility`
的 `attributed` 恒空、中性措辞、不栽成用户造成。诊断只读候选池、一趟 `combinations`、不触发
第二次整解搜索，也不声称哪条锁「该负责」——守住既有免责边界。前端 `NoSolution` 从光秃秃
一句升级成原因 + 归因 chips，warning/中性双档 token，固定顺序，退回逻辑与免责句保留。

### 应用期两个坑

1. **资格挡线原来进不了 `infeasible_line`。** `legal_pairs` 只过 slot/gap/cap，不看资格
   （资格只在搜索递归 `_eligibility_ok` 事后拒绝），所以「某人被限制在别线」永远不会让本线
   `options` 变空 → 资格原因无从触发。`restricted_to_lines` 是「队员×线」的局部可判事实
   （`check_locks` 早就这么判锁定对），故把同一条过滤并入 `legal_pairs`：更早、据实剪枝，
   SILVER（无 restriction）不受影响，全套既有测试通过。已写进 design/README。

2. **`uvicorn --reload` 在本机僵尸占端口。** Application Control 拦 reload watcher 子进程
   （主进程 exit 127），但它 spawn 出的 worker 继承了监听 socket 活下来，8011 一直
   LISTENING 而 owner PID 已死——taskkill 说进程不存在、新 uvicorn bind 报 WinError 10048、
   僵尸还在发旧代码（据此误判过一次代码没生效）。要 `Get-CimInstance Win32_Process` 找
   `spawn_main` 子进程杀掉。上个 session 遗留的 worker 也这么占着。以后起后端一律裸 uvicorn。
   已沉进 CLAUDE.md pitfalls。
