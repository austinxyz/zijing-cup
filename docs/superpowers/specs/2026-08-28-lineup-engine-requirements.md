# lineup-engine Requirements

把「这十个人这么排，合不合法、还能不能更强」变成系统能回答的问题。规则数据
（`competition-rules`）与名单数据（`team-roster`）都已上线，这是第一个真正消费两者
的能力。

队长的实际动作是：锁住几对已经定下的搭档，让引擎在规则允许的范围内补齐其余，
并告诉他这支队最多能部署多少实力、他现在这套差多少。

## Goals

- **合法性校验**：给定一套完整或部分阵容，回答合不合法，以及**具体是哪条约束
  被碰到**——逐线 cap、全队共享 buffer 预算、搭档 UTR 差距 ≤3.50、三线男双非递增、
  高 UTR 人数上限。不合法时要说清哪一条、差多少。

  高 UTR 限制在金组**不只是人数**：UTR>9.0 的男队员不超过 1 名**且只能打 D1 或 MD**。
  只查人数会放出「把这名队员排进 D2」的非法阵容。
- **补齐搜索**：锁定若干条线的搭档、排除若干名本场不能上的队员后，引擎在剩余空间里
  搜出合法阵容，按**上场十人参赛 UTR 总和**从高到低排。
- **上限报告**：给出这支队在当前锁定与排除下能达到的总和上限，以及**有多少组不同的
  十人**能达到它。这比「前五名」更诚实——目标会顶满预算然后大面积并列。
- **候选按十人组合去重**：同一批十人在五条线上换位置不算两套阵容。
- 两个组别共用一套引擎：金组的开放线表达为「无上限」，不是一个很大的数字。
- 搜索有节点预算；触到预算必须**明说被截断**，不得把截断结果当作完整搜索呈现。
- **一个能用的排阵页面**（本 change 含界面，不拆）。侧栏导航项叫**「阵容」**，
  不叫「分析」——「分析」是对手对比那个功能的名字（本次 Non-Goals 第一条），
  两者同名会让人以为已经能比对手了。对手对比在侧栏里保留为「未开放」项。
  - 五条线各有一个锁定控件，可指定该线两名队员或留空交给引擎；另有一份「本场不能上」
    的排除名单。两者都反映在 URL 里，刷新与分享链接不丢。
  - 结果区呈现：总和上限、有多少组不同的十人能达到它、以及去重后的候选列表。
    每套候选显示五条线的搭档、各线相对 cap 的余量、以及该套用掉多少 buffer。
  - 三种非正常状态各自有明确呈现：**无解**（锁定或排除导致）、**搜索被截断**、
    **外援限制未校验**。三者都不得以「结果为空」或静默省略的方式表达。
  - 无解的诊断做到**「哪条线凑不出，以及那条线的候选为什么空」**这一级：既说「WD 没有
    合法搭档」，也可以直接读出当前锁定与排除下每名队员的去向（谁被锁进了别的线、谁被
    排除），因为那是读状态，不需要重新搜索。
    **不做「是哪一条锁定该负责」**——那要逐条去掉锁定重算，最多五次完整搜索，在 Render
    上代价不成比例，且多条锁定共同导致时仍然指不准。界面上必须说清这个区别，不能让
    「谁去了哪」被读成因果归属。

## Non-Goals

- **不做对手对比。** 设计稿 `design/Analysis.dc.html` 画的是双方各自排阵、逐线对比、
  给出胜场预估。那需要先定义「同一条线谁占优」的判定方式（一个概率模型），而且交表
  之前拿不到对手阵容。另开 change。
- **不做胜负预测**，不给任何形式的赢面百分比。
- **不做外援限制校验。** 规则对外援有每队名额与每场上场人数限制，但每场上限取决于
  该队联合了几所学校，系统里没有这个信息（见 `docs/domain/rules.md`「已澄清」§3）。
  引擎**不假装能校验**：结果里要明说这一项没有校验。
- **不做金组 4:4 平局的第一级抢先**（净胜局百分比，需要真实比分）。见下方 Constraints
  中关于目标函数与第二级抢先方向相反的说明。
- **不持久化任何东西。** 锁定与排除都进 URL，不入库，没有「保存我的阵容」。
- 不做移动端版式（`mobile-shell` 未做，壳层仍无窄屏布局）。

## Constraints

- 引擎在 FastAPI 侧。领域规则只由后端实现——前端算一遍等于第二份规则实现。
- **接口是 GET，锁定与排除进 query 参数。** 现有 `team-roster` spec 有一条断言
  「OpenAPI 里不存在任何写方法」并有测试守着，本次不放宽它。GET 还白送两个属性：
  阵容链接可以直接发给队友，且与前端既有的「URL 是唯一事实来源」一致。
- cap / buffer / 资格阈值全部从 `competition-rules` 的数据读取，**一个都不许写成常量**。
  金组的开放线是 `cap IS NULL`。
- Buffer 是**全队共享预算**：各线超出量之和不得超过额度。逐线判定会放出五线各超 0.2、
  合计 1.0 的非法阵容。
- 女队员可以打男队员的位置；此时按男队员的资格限制判定。
- 参赛 UTR 全程用 Decimal，不经过浮点。10.25 与 10.2 对 cap 是不同的答案。
- Render 免费实例的 CPU 比开发机慢数倍，且闲置后冷启动接近一分钟。搜索必须有节点
  预算，超出即截断并如实报告。
- **目标函数与金组 4:4 的第二级抢先方向相反。** 那一级是「上场十人总 UTR 低者胜」，
  而本引擎最大化总 UTR。结果呈现时不得暗示「顶满 cap 在任何情况下都占优」。
- 名单含真实校友姓名与 UTR：测试一律使用虚构姓名。

## Success Criteria

- 对 2025 全部 24 支球队（金 6 + 银 18）执行无锁定搜索，全部返回结果或如实报告截断；
  单次搜索在开发机上不超过 3 秒。
- 银组某队的搜索结果满足：每条线的两人参赛 UTR 之和不超过该线 cap 加**每线** buffer；
  五线超出量之和不超过**全队** buffer 额度；三条男双线的和非递增；每对搭档差距
  ≤3.50；高 UTR 人数不超过该组别的上限。
- 金组的开放线（D1 / MD）不参与 cap 校验，也不消耗 buffer 预算。
- 上限报告给出的总和，确实没有任何合法阵容能超过（与一次完整搜索的最大值一致）。
- 锁定一对搭档后重新搜索，所有结果都包含该对；锁定使结果无解时，明确报告无解
  **而不是返回空列表**——空列表读作「搜过了没有」，与「你锁死了」是两回事。
- 排除某名队员后，所有结果都不含该队员。
- 候选列表中不存在两套「十人相同、仅换线」的阵容。
- 校验一套不合法阵容时，返回的每一条违规都指明线位与差额（例如「D2 超 cap 0.35，
  全队 buffer 仅剩 0.15」）。
- 结果中明确标注外援限制未校验。
- 新增的端点是 GET；`test_no_write_route_exists` 仍然通过，OpenAPI 里依旧不存在任何
  POST / PUT / PATCH / DELETE。
- 金组某队的搜索结果中，UTR>9.0 的男队员若上场，只出现在 D1 或 MD。
- 页面上锁定一对搭档后，地址栏随之改变；直接访问该地址得到同一套锁定。
- 候选阵容里显示每名队员的性别——高 UTR 上场限制是分性别的（>7.0 男 ≤1、>5.5 女 ≤1），
  不显示性别就无法据界面核对这条约束。
- 三种非正常状态（无解 / 被截断 / 外援未校验）在页面上各自可见，且都不是空列表。
- 构造一组必然无解的锁定（例如把两名女队员同时锁进两条不同的线，使 WD 无人可用），
  返回的无解信息指名是哪条线凑不出。
- 客户端 bundle 不含 `BACKEND_URL` / `BACKEND_SECRET`。

## User Stories

- 作为队长，我已经定了 D1 和混双的搭档，想让系统在剩下三条线里给我几套合法的排法，
  而不是我拿计算器逐对试 cap。
- 作为队长，我想知道我这支队理论上最多能部署多少实力、我现在这套差多少——差得多
  说明我还有牌没打出来。
- 作为队长，我排完想确认它真的合法：五条线的 cap、全队 buffer、搭档差距、男双不倒序、
  高 UTR 人数，一次全查完，而不是漏掉一条到了赛场才被判无效。
- 作为队长，本周有两个人来不了，我想把他们排除掉再算。
- 作为队长，当我锁的搭档让阵容凑不出来时，我想知道是锁死了，而不是以为系统没搜到。

## Open Questions

留到视觉稿阶段（Phase 4）：

- 「上限 56.00 / 有 177 组不同十人能达到」这句话在界面上怎么放，才不会读成「有 177
  套推荐」。
- 无解时那句「WD 找不到合法搭档」放在结果区哪个位置、用什么强度呈现。
- 「外援未校验」这条免责放在哪里，才既看得见又不喧宾夺主。
- 设计稿 `design/Analysis.dc.html` 是双方对比版，本次范围是单队，需要新画单队版式。

## 探索阶段测得的事实

写进需求文档，因为它们决定了实现方式，且重测一次代价不小。

**穷举是可行的。** 分支限界（按合法搭档数从少到多定线序：WD → MD → D3 → D2 → D1，
以「剩余各线最强搭档之和」为上界剪枝）在开发机上跑完 2025 全部 18 支银组球队，
最坏 1.61 秒（`SJTU-XJTU`，346 万节点），多数队低于 0.05 秒；金组 6 队最坏 0.21 秒。
**不需要启发式，也不需要策略模式**——路线图里「移植 MatchApp 策略模式引擎」的前提
（搜索空间过大）不成立。

原始空间确实很大（完整阵容组合数 24 万 ~ 288 亿），塌下来是因为：女双合法搭档极少
（3~35 对，女队员本就少）、cap 逐线收紧、且目标函数一旦拿到接近上界的现任解就能
大面积剪枝。

**并列极其严重，且分两种性质。** `UCSD-ZJU-MU` 与 `USTC-CMU-HQU` 的最优值 56.00
（= 五线 cap 之和 55.5 + buffer 0.5）各有 400 套以上并列，其中 175 / 177 组是**不同的
十人**——那是真正的选择。而 `JLU-UESTC`、`NYU-UMICH`、`SJSU`、`SJTU-XJTU`、
`SYSU-UCLA-UCD` 同样有 270~315 套并列，却**只有 1 组十人**——同一批人在五条线上
换位置。后者若按「Top 5」呈现，等于把同一套阵容重排五遍冒充五个选项。这是「报上限 +
按十人去重」这个决定的直接依据。

**金组的开放线不会导致目标失真。** 曾担心「总和最大」会把实力堆到只值 1 分的 D1/MD。
实测 `THU-UOC` 的最优解：D2/D3/WD 全部顶死在 cap 上（合计仅超 0.29，正好在 0.3 预算内），
多出来的实力没有别处可放，只能进开放线——而开放线每条仍值 1 分。所以目标在两组都成立。
唯一的代价是它与 4:4 的第二级抢先方向相反，已记在 Constraints。
