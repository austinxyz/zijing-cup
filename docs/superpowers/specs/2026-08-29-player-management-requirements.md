# player-management Requirements

把「队员」从名单快照里的一行，变成可以跨年维护的实体。

现在的 `roster_entries` 是按 `(赛季, 组别)` 存的快照，刻意没有 `players` 表——当初的
理由写在 migration 注释里：组委会总表不带 UTR 档案 ID，跨年身份无法从数据里证明，
按姓名归并会把它猜错。本 change 正面回答那条决定：**身份仍然靠猜（按姓名起 id），
但猜错了人能改**——admin 可以合并两个其实是同一个人的条目，也可以拆开一个其实是
两个人的条目。

这也是本项目第一次有**写接口**。现有后端有一条被测试钉住的断言：OpenAPI 里不存在
任何 POST/PUT/PATCH/DELETE。那条断言这次要被打破，因此鉴权不是实现细节，是前提。

## Goals

- **队员实体**：新建、修改、删除队员。字段为姓、名、性别、当前单打 UTR 与其状态、
  当前双打 UTR 与其状态、UTR 档案链接。两个当前 UTR 的状态各自取 `unrated` /
  `projected` / `rated`。

  这**不是**参赛 UTR 那三档的中英文版本，两者是不同的东西：当前 UTR 的状态是 UTR 官网
  自己的评级状态；参赛 UTR 的状态是组委会对参赛值的**认定方式**，其中「队长评定」在
  官网侧根本没有对应物。两个枚举各自独立，不共用一张表、不互相推导。
- **参赛 UTR 按赛季**：一名队员每年一个参赛 UTR（`player_season_utrs`，键为
  `(人, 赛季)`），状态取**已认证 / 组委会审定 / 队长评定**三档，**Appeal 是可叠加在
  任一档上的独立标记**，不是第四档。
- **参赛 UTR 可以先用当前 UTR 预填**，等组委会的总表到了再覆盖。因此每条赛季 UTR 带一个
  **来源**字段：`预填`（取自当前 UTR，是个猜测）/ `组委会总表`（权威值）/ `admin裁决`
  （冲突裁决的结果）。没有这个字段，预填值和冻结的官方值在库里长得一模一样，取大规则与
  cap 判定就会把猜测当权威值用。现有 `roster_entries.source_note` 已经是同一个用途的
  先例（2025 数据里存的是 `Captain Provided UTR` / `Zijing Cup 2024 UTR`）。
- **队伍成员关系**：把队员加入/移出某支队伍（队伍属于某个 `(赛季, 组别)`）。成员关系
  上带**代表学校**、**是否外援**、**是否外卡**。同一名队员可以同时属于同赛季的金组与
  银组两支队（规则允许），因此成员关系是多条并存，不是一对一。

  三个字段的确切含义（**外援与外卡听起来近，约束完全不同，不可混用**）：
  - **代表学校**：自由文本，不关联学校表。队伍 code 本身就是 `ZJU-USC`、`SJTU-SJSU-ECU`
    这种拼出来的字符串，现有 schema 明确不拆分、不归并、不做别名合并（总表里同一支队
    在不同 tab 拼法都不一样）；建一张学校表会立刻面对同一个别名问题。
  - **是否外援**：受规则硬约束——每队有名额上限、每场有上场人数上限。系统**不校验**这
    一条（每场上限取决于该队由几所学校组成，这个信息不在系统里），排阵结果里始终标注
    「外援限制未校验」。这个字段只是记录，不是判定依据。
  - **是否外卡**：表示该队员不属于当前学校，**不影响上场资格**，但需要组委会同意。
    纯标注，不参与任何判定。
- **队员独立于队伍存在**：一名队员可以不属于任何队伍，仍然可维护。
- **合并与拆分**：
  - 合并两名队员为一名。合并后若同一赛季出现两个不同的参赛 UTR，**标记为未裁决**，
    不阻塞合并。
  - 拆分一名队员为两名，由 admin **逐行勾选**每条赛季 UTR 与每条成员关系归属哪一边。
- **未裁决冲突的取值规则**：裁决之前，任何消费参赛 UTR 的地方**取较大的那个值**，并在
  结果里标明「本结果含 N 名参赛 UTR 未裁决的队员」。

  本 change 只**定义**这条规则并在管理界面呈现未裁决队列；排阵页真正显示这个标记要等
  读路径切过来（change C）——在那之前排阵引擎读的还是旧表，旧表里没有「未裁决」这个
  概念，本 change 内无法达成，也不该写成本次的验收。
- **管理员写入口**：Next 侧登录（口令 → httpOnly cookie），FastAPI 侧写路由额外要求
  `X-Admin-Secret`。读路由维持现状不变。
- **管理界面**：队员列表与检索、队员编辑、赛季参赛 UTR 维护、队伍成员维护、
  合并/拆分、未裁决冲突队列。
- **迁移**：把线上 `roster_entries` 的 **2025 与 2026 两季全部行**迁进新表。迁移后新表
  是队员数据的唯一事实源。

## Non-Goals

- **不切换读路径**（留给 change C，**紧接本次**）。`team-roster` 与 `lineup-search` 本次
  继续读 `roster_entries`。后果必须说清：**本 change 落地后到 C 落地前，管理员在管理
  界面里做的任何修改，在球队名单页与排阵页上都看不见**——那两个页面读的还是旧表。所以
  C 排在 B 前面，且应当紧接着做。
- **不改名单 CSV 导入器**（留给 change B）。导入器现在写 `roster_entries`；本 change
  落地后到 B 落地前**暂停名单导入**，名单变更走管理界面。这是有意接受的窗口，理由见
  Constraints。
- **不做多角色权限**。只有一个管理员。队长/球员分级权限仍是 CLAUDE.md 里那条「未来要
  重新设计」的事，本次不在共享密钥模型上打补丁去逼近它。
- **不做 UTR 同步**。当前单打/双打 UTR 由人工录入，不去 UTR 官网抓。
- **不做审计日志/操作历史**。合并与拆分不可撤销这一点要在界面上说清楚。
- **不做移动端版式**。管理界面是桌面场景。

## Constraints

- **写接口必须默认关闭。** `backend/app/auth.py` 的中间件是**减法式**的：新路由不声明
  就已经被共享密钥保护。写路由的 `X-Admin-Secret` 检查必须沿用同一种形状——默认拒绝，
  而不是「记得加装饰器才拒绝」。缺失的密钥必须意味着「谁都进不来」，不是「谁都能进」。
- **共享密钥不进浏览器。** 现有验收里有一条「客户端 bundle 不含 `BACKEND_SECRET`」，
  `X-Admin-Secret` 同样只能存在于 Next 的服务端。登录 cookie 必须 httpOnly。
- **窗口期暂停导入。** 本 change 落地到 B 落地之间跑一次名单导入会写旧表而不写新表，
  两边分叉。这段时间名单变更只走管理界面。2026 赛季 9 月中开打，总表一季来一两次，
  若窗口期内真来了新版总表，先做 B 再导。
- **落地顺序是 A → C → B。** C（读路径切换）是纯技术改动、没有产品决策，先做它可以把
  「管理员改了前台看不见」这个窗口压到最短；B（导入器）排最后，因为导入本来就暂停着。
- **迁移不得自行裁决冲突。** 现有 2025 数据里有 17 个人在金银两组各有一行且参赛 UTR
  不同（见「探索阶段测得的事实」）。迁移必须把它们标成未裁决，不能挑一个值写进去——
  挑错会静默改掉某一组的 cap 判定。
- **未裁决时取大是有代价的选择。** 参赛 UTR 在规则里几乎全部用作**上界**判定（逐线
  cap 是「两人之和 ≤ cap」，高 UTR 限制是「超阈值人数 ≤ N」）。取小会把一套其实违规的
  阵容显示成合法，赛场上才暴露；取大只会少给几个本来合法的选项，是看得见的。因此取大。
- **删除只在没打过或赛前。** 一名在 2025 打过的队员，其历史成员关系与赛季 UTR 是历史，
  删掉等于改历史。赛季可以被**锁定**，锁定后该赛季的数据不可删改。锁的粒度是**赛季**
  （不按组别细分）。
- **`Decimal` 全程。** 参赛 UTR 与当前 UTR 都是精确小数，10.25 与 10.2 对 cap 是不同
  答案。任何一处退化成 float 只在边界上出错，而边界正是最难发现的地方。
- **schema 隔离照旧。** 所有新表建在 `zijing_cup` schema，migration 文件以
  `set search_path to zijing_cup, public;` 开头。远程不跑 CLI push，去 Dashboard 手工
  执行。
- **合并/拆分不可撤销。** 本次不做审计日志，因此界面必须在执行前说清后果。

## Success Criteria

- 管理员登录后可以新建一名队员、改其字段、删除一名没有任何成员关系的队员；未登录时
  这三件事都做不到，且未登录时读页面照常工作。
- 未带 `X-Admin-Secret` 的写请求返回 401/403；`X-Admin-Secret` 未配置时**所有写请求
  都被拒绝**（而不是全部放行）。
- 一名队员可以同时是 2025 金组与 2025 银组两支队的成员，两条成员关系各自带自己的
  代表学校/外援/外卡标记。
- 一名队员在 2025 与 2026 各有一个参赛 UTR，互不影响。
- 迁移跑完后：新表的队员数等于线上 `roster_entries` 按**规范化姓名**（两栏各自 `trim` 后
  转小写，再拼接）去重后的人数；两季全部行都有对应的成员关系；那 17 个金银两组值不同的
  人被标为**未裁决**，且未裁决数正好是 17。规范化规则必须写死并有测试——不规范化的话
  `Xie Yuntao "Young"` 这类带引号别名与大小写差异会各成一人，验收标准就不可判定。
- 合并两名队员后，两边的成员关系与赛季 UTR 全部挂到同一个人名下；同赛季两个不同值
  被标为未裁决而不是被静默丢弃一个。
- 拆分时 admin 勾选的每一行都落到他指定的那一边，没勾的留在原处。
- 未裁决的赛季 UTR 被读取时取较大值（本次以单元测试证明取值规则；排阵页上的呈现属于
  change C 的验收，不是本次的）。管理界面有一个未裁决队列，迁移后里面正好 17 条。
- 赛季锁定后，该赛季（两个组别一起）的队员删除与赛季 UTR 修改被拒绝，且拒绝理由指明
  是赛季锁。
- 用当前 UTR 预填出来的赛季 UTR 来源是 `预填`；被组委会总表覆盖后来源变成
  `组委会总表`；界面上能把两者分开看。
- 客户端 bundle 不含 `BACKEND_SECRET` / `X-Admin-Secret`；登录 cookie 是 httpOnly。

## User Stories

- 作为管理员，我想在 UTR 官网查到一个新人之后，直接在系统里建一条队员记录，填上他的
  UTR 链接和当前单双打 UTR，**而不必等一份新的组委会总表**。
- 作为管理员，我想把一名队员加进 2026 银组的某支队，并标注他代表哪所学校、是不是外援、
  是不是外卡——这些是队伍层面的身份，同一个人在另一组可以不一样。
- 作为管理员，我想看到系统认为「可能是同一个人」的两条记录，确认后把它们合并；也想在
  发现两个同名的其实是两个人时，把已经合并的拆开，并逐行决定哪条记录跟谁走。
- 作为管理员，我想知道哪些人的参赛 UTR 还没裁决，因为在裁决之前排阵结果是保守估计。
- 作为管理员，我想在一个赛季打完之后锁住它，避免有人手滑改掉已经比过的数据。

## Open Questions

- **范围偏大，本次不拆**（已确认）。本 change 同时包含新数据模型、迁移、第一次写接口与
  鉴权、登录页、管理界面 CRUD、合并/拆分与冲突队列。上一个 change 是 6 组 13 个 commit，
  这个只会更多。不拆是明确的决定，代价是任务组会更长、评审轮次会更多——propose 阶段要
  按这个体量安排任务组，不要按上一个 change 的规模估。
- **删除的确切语义**：真删除行，还是标记为「不再参赛」并保留历史？Constraints 已定
  「只在没打过或赛前允许」，但「打过」的判定依据是什么——赛季锁，还是别的标志？
- **合并的候选怎么找**：系统主动扫同名并推荐，还是完全由 admin 手工发起？若主动推荐，
  按精确同名还是也做模糊匹配（大小写、空格、`Xie Yuntao "Young"` 这种带引号别名）？
- **登录口令怎么存**：环境变量存哈希（bcrypt/argon2）还是明文比对？会话多久过期？
  失败要不要限速？倾向哈希 + 有限期 cookie + 简单限速，propose 阶段给具体方案。
- **未裁决标记的可见范围**：只在管理界面可见，还是排阵页也要显示？Success Criteria 暂
  按「排阵页要显示」写，待确认是否过度。

## Referenced Capabilities

- `team-roster` —— 现有的名单快照与只读端点。本 change 不改它的读路径，但迁移要读它
  全部的行，且新表落地后它变成派生物。
- `competition-rules` —— 赛季与组别的定义（`divisions` 表），新表的成员关系要挂在它
  定义的 `(赛季, 组别)` 上。
- `lineup-search` —— 参赛 UTR 的消费方。未裁决取大与「含 N 名未裁决」的标记最终要在
  这里体现（读路径切换在 change C，本次只定契约）。
- `app-shell` —— 管理界面要进侧栏；登录态的呈现（登录/登出）也在壳里。

## 探索阶段测得的事实

以下数字来自本地 2025 真实数据（459 行，经运行中的后端 API 逐队读出），不是估计：

- **459 行** = 2025 金组 120 + 银组 339；**375 个不同姓名**。
- **83 个姓名出现在多行**，其中 **82 个**是「同一赛季、金银两组各一行」——规则允许同一
  人两组都打，所以这是正常状态，不是脏数据。**0 个**姓名在同一支队里出现两次。
- **83 个重名里有 17 个两行的参赛 UTR 不同**，全部是清华的人（金组 `THU-UOC` 对银组
  `THU-I`/`THU-II`）：Liu Rayne 7.82/7.84、Yang Alex 7.65/7.70、Zong Qingqing
  **6.25/6.38**、Li Fred 6.69/6.74……两张总表分别冻结，取样时点差了几天。这 17 个就是
  迁移后第一批未裁决冲突。
- **459 行里带 `utr_profile_id` 的：0 行。** 字段早就存在但从未被填过。也就是说今天
  库里**没有任何身份证据**，按姓名起 id 是唯一可行的起点。而 UTR 链接是本次队员字段
  之一，往后它才是让合并变得可验证的那个键。
- 状态分布：`Rated/verified` 358、`Projected/committee` 58、`Unrated/(空)` 33、
  `Projected / Appeal` 5、`Unrated / Appeal` 3、`Rated / Appeal` 2。
  **`Appeal` 三种档位上都出现过**，这是把它做成独立标记而不是第四档的直接依据。
  **`self_rated`（队长评定）一行都没有**——33 行 `Unrated` 的评级类别全是空的，
  等组委会澄清。

## Design System

沿用本项目已定型的设计系统，**不引入新风格**：`frontend/app/globals.css` 的 token 块
（逐值移植自 ai-course-management）与 `components/ui/` 的 Button/Card/Badge/Input。
理由是 `app-shell` 那条能力里已经写下的那句——两个应用要看起来是一家人，
「重新推导出的差不多配色」正是这件事悄悄失效的方式。

（`awesome-design-md` 技能在本机未安装；即便装了，本次也不该重选风格：管理界面与
已上线的规则页、名单页、排阵页处在同一个壳里，换风格会让同一个侧栏下面出现两套观感。）

视觉稿：`docs/superpowers/specs/mocks/2026-08-29-player-management-mocks.html`，
核心五屏——登录、队员列表、队员详情（基本信息 + 各赛季参赛 UTR + 队伍成员关系）、
拆分（合并同骨架反向）、未裁决冲突队列。桌面 1440×720；移动端不在本 change 范围
（管理界面是桌面场景，见 Non-Goals）。

每屏下方写的是**为什么这么画**，实现时要照着核对的是那些理由，不是像素：
- 登录屏默认画出失败态与剩余次数——限速只在后端存在、前端不说，会被当成自己手滑。
- 列表的「参赛 UTR」列把 `未裁决` 与 `预填` 用同一档警示色：它们是同一类事——
  这个数字还没被组委会确认。
- 详情屏的未裁决横幅写明「按较大值 6.38 计算」，不只说「有冲突」：保守取大是会影响
  排阵结论的规则，藏在文档里等于没有。
- 拆分屏两侧同时显示拆完的结果，而不是只勾一列；「证据」列放 UTR 链接，因为那是唯一
  能证明两条记录是不是同一个人的东西（而库里现在一条都没有）。
- 不可撤销的操作用 danger 色，与 `未裁决` 的 warning 分开：两者不是同一类事，
  同色会让人以为都只是「注意一下」。
- 队列屏的「全部按较大值确认」不是主按钮：它把「保守估计」变成「已确认的事实」，
  不该长得像默认动作。
