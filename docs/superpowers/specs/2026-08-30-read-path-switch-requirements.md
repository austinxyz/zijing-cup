# read-path-switch Requirements

把 `team-roster` 与 `lineup-search` 的读取来源从名单快照（`roster_entries`）换成
队员注册表（`players` / `player_season_utrs` / `player_team_memberships`）。

上一个 change 建好了新表并迁完了数据，但读取仍走旧表——后果写在它的 Non-Goals 第一条：
**管理员在管理界面里做的任何修改，在球队名单页与排阵页上都看不见**。本 change 就是关掉
这个窗口。

技术上是「换一个数据来源」，但有两处不是纯技术：新模型能表达旧表表达不了的状态
（在队里但今年没有参赛 UTR），而阵容锁定的 URL 里嵌着旧表的主键。

## Goals

- **三处读取切到新表**：球队列（人数与男/女构成）、球队名单页、排阵引擎的名单读取。
  切换后这三处呈现的是管理界面里的数据，改一个字段就能在前台看见。
- **参赛 UTR 的推导链**。新模型允许「有成员关系但该赛季没有参赛 UTR」，旧表不允许
  （`match_utr` 是 NOT NULL）。排阵取值按组委会自己的规则逐级回退：

  1. 本赛季的 match UTR（冻结值）→ 来源 `组委会总表`
  2. 当前**双打** UTR 且其状态为 `rated` → 来源 `估算（当前已认证值）`
  3. 当前双打状态为 `projected` 或 `unrated` → 往前找**最近一个有值的赛季**的
     match UTR（不限于去年）→ 来源 `估算（<年份>参赛值）`。标记 MUST 带上年份：
     用 2025 的值估 2026 与用 2023 的值估 2026 是两种可信度，标签把年份吞掉就等于
     把这个差别吞掉了。
  4. 都取不到 → 由 admin 手工输入；在此之前该队员**不参与排阵**，且结果里要说明
     「本队 N 人因缺少参赛 UTR 未参与计算」

- **推导链在名单页与排阵引擎上是同一条**。同一名队员在两个页面必须给出同一个数字：
  推导链是组委会的算法，不是排阵的内部技巧，两处给出不同答案比多标一次估算更难解释。
  名单页对推导出来的值同样要标估算与年份。
- **估算值必须看得见，而且标三处**：那名队员的数字旁、整套候选阵容上、以及顶部的
  可达上限。合法性是**整套**的属性——五条线的和、全队 buffer、高 UTR 人数都会用到那个
  数字，所以一套阵容里只要有一个估算值，「这套合法」这个结论本身就是估算。
- **兑现上一个 change 推过来的那句**：排阵结果要呈现「含 N 名参赛 UTR 未裁决的队员」。
  未裁决取较大值这条规则此前只在管理界面可见，切换后它开始影响排阵结论，就必须在
  排阵页上说出来。
- **阵容锁定的 key 换成带前缀的形式**（如 `p10531`），使旧链接里的裸数字**解析失败**。
- **导入器要挡住自己**：切换后它写的是没人读的表，必须拒绝运行或在输出里刺眼说明，
  不能只靠「说好了暂停」。

## Non-Goals

- **不做当前 UTR 的来源**。`players.singles_utr` / `doubles_utr` 及其状态由项目负责人
  自行导入或在管理界面编辑，本 change 不加同步、不加批量导入。名单页要写明这一列是
  人工维护、未同步——否则一整列「—」读起来像坏了。
- **不改名单 CSV 导入器的写入目标**（那是下一个 change）。本次只让它在切换后不再
  制造「成功的假象」。
- **不删 `roster_entries`**。它保留为只读，是回滚依据：新表出问题时，把读取切回去就能
  回到今天的状态。
- **不搬 `dutr_status` / `source_note` / `daily_utrs`**。赛季那一层只需要 `match_utr`；
  「这个值怎么来的」由 `source` 字段和推导链表达。三个字段**保留在 API 响应里**（值恒为
  null）以免改动响应形状，但界面 MUST NOT 再从它们身上渲染任何东西——一个永远为 null
  的字段被渲染出来，读起来是「总表没说」，而事实是「我们不再存了」，这是两件事。
  代价见 Constraints。
- **不做移动端版式。**

## Constraints

- **名单页会少一样东西：总表原文。** 现在的「UTR 来源」列同时给出判定词（已认证 /
  委员会审定 / 待定）与总表的原始状态词（`Rated`、`Projected / Appeal`……）。新模型没有
  后者，切换后这一列只剩判定词。这是有意接受的：赛季那层只留 `match_utr`。但要意识到
  代价——**拿页面去跟组委会的表逐行对账这件事，之后做不了了**。
- **估算值会进 cap 判定。** 第 2、3 步取到的数字不是冻结值，却会参与逐线 cap、全队
  buffer 与高 UTR 人数的判定。这是明确接受的取舍（项目负责人在探索阶段确认过两次），
  代偿手段只有一个：**标出来**，见 Goals 第三条。MUST NOT 在任何地方把估算值与冻结值
  呈现成同一种东西。
- **旧的阵容链接必须响亮地失败。** 锁定写在地址栏里（`?D1a=10531`），那个数字今天是
  `roster_entries.id`，切换后同一位置会被读成 `players.id`——两套 id 互不相干但都是整数。
  恰好也存在时，页面会算出一套看着合法的阵容而锁的是两个不相干的人，屏幕上没有任何
  提示。因此新 key MUST 是旧格式解析不出来的形式，且失败时 MUST 说明是链接过期而不是
  一个笼统的 4xx。
- **切换后导入器会制造成功的假象。** 它会照常输出「+N 行」而网站上什么都不变。
  见 Goals 最后一条。
- **`Decimal` 全程。** 推导链里的每一步都是精确小数，10.25 与 10.2 对 cap 是不同答案。
- **排阵的性能不能退化。** 现在读一支队的名单是一次查询；切换后要读成员关系 + 队员 +
  赛季 UTR（+ 回退时还要读更早赛季的值，且回退不限于一年）。MUST NOT 变成按人一次查询——2025 最大名单 26 人，
  24 支队全搜一次的实测最坏是 0.09 秒，这个数量级要保住。

## Success Criteria

- 在管理界面改一名队员的姓名或参赛 UTR，刷新球队名单页与排阵页能看到改动。
- 球队列的总人数与男/女/未知三档人数，与该赛季各队的成员关系统计一致；性别为空的
  仍单列第三档，不并进任何一侧。
- 一名在队但当年没有参赛 UTR 的队员：按推导链取到值时参与排阵且被标为估算；四步都
  取不到时不参与，且结果里报出「N 人未参与计算」。
- 同一名缺值队员在名单页与排阵页上显示同一个推导值与同一个估算标记。
- 第 3 步取到的值，其标记写明来自哪一年（例如「估算 · 2025 参赛值」），而不是笼统的
  「去年」。
- 一套含估算值的候选阵容，在队员、候选、可达上限三处都能看到估算标记。
- 排阵结果呈现「含 N 名未裁决」；N 与管理界面未裁决队列的条数一致。
- 用旧格式（裸数字）的阵容链接访问排阵页：返回 4xx 或明确的页面提示，**MUST NOT**
  渲染出一套锁定了其他人的阵容。
- 切换后运行名单导入器：命令拒绝执行或输出中明确指出这些行不会出现在任何页面上。
- 2025 全部 24 支球队各搜一次仍在秒级完成。回归判据是**数值**逐项一致：可达上限、
  达到上限的十人组合数、去重后的候选套数，以及每套的总和与各线之和。
  **MUST NOT 要求候选列表逐字相同**——搜索按 `key` 排序来保证并列时次序可复现，而 key
  从 `10531` 变成 `p10531` 会改变字符串序，因此并列部分「前 20 套具体是哪 20 套」可能
  与切换前不同。次序仍必须在同一输入下可复现，这条不变。
- 客户端 bundle 不含 `BACKEND_SECRET` / `ADMIN_SECRET`。

## User Stories

- 作为管理员，我在管理界面改完一名队员的参赛 UTR，想立刻在排阵页看到新的候选，而不是
  怀疑自己没保存成功。
- 作为队长，我想在 2026 总表出来之前就先排排看——用去年的参赛值估算也行，但我要一眼
  看出哪些数字是估的，别把估算结果当成定论发给队友。
- 作为队长，我打开一条上周分享的排阵链接时，宁可看到「这个链接过期了，请重新选人」，
  也不要看到一套锁着两个陌生人的阵容。
- 作为管理员，我不小心跑了一次名单导入时，想被告知这次导入不会影响任何页面，而不是
  看到「+30 行」然后困惑于网站为什么没变。

## Open Questions

- **`roster_entries` 切换后的去留**：倾向保留只读作为回滚依据，直到导入器那个 change
  落地后再决定退休。需要确认没有别的东西还在依赖它（迁移命令仍要读它）。
- **推导链要不要写进 `docs/domain/rules.md`**：它是组委会的算法而不是本系统的发明
  （`roster.md` 里记着「Rated 直接用当前值；Projected 用去年 Rated override」），
  规则文档里可能该有它的位置。

## 视觉改动（不出 mocks）

没有新页面，改的都是往既有组件上加标记，因此本次**不产出视觉稿**：逐字文案与色档在这里
写死，实现时对照现有页面核对（名单页 `teams/[code]`、排阵页 `lineup/[code]`）。

**色档沿用既有三档，不新增**：

| 档 | token | 本次用在哪 |
|---|---|---|
| warning | `--color-warning-surface` / `-border` | 「估算」「未裁决」——两者同属「这个数字还没被组委会确认」 |
| danger | `--color-danger-*` | 本次**不用**。旧链接失效是提示，不是危险操作 |
| 中性 | `--color-border` / `bg-surface` | 「N 人未参与计算」、旧链接失效的说明 |

**逐字文案**：

- 名单页缺值队员的参赛 UTR：`估算 · 2025 参赛值`（年份取实际取到的那一年）；
  取自当前双打值时为 `估算 · 当前已认证值`
- 名单页当前 UTR 列的说明：`当前 UTR 由人工维护，未与 UTR 官网同步`
- 排阵页候选里某个数字旁：`估算`
- 排阵页整套候选上：`含 N 个估算值，合法性待总表确认`
- 排阵页可达上限旁：`含估算值`
- 排阵页顶部：`本结果含 N 名参赛 UTR 未裁决的队员，按较大值计算`
- 排阵页顶部：`本队 N 人因缺少参赛 UTR 未参与计算`
- 旧链接失效：`这个链接是旧格式（队员编号已变），请重新选择锁定的搭档`

**要盯的一件事**：排阵页顶部现在可能同时出现「未裁决」「未参与计算」「搜索被截断」
「外援限制未校验」四类提示，候选卡上还有「估算」。实现时若发现顶部变成一片提示墙，
就是信息结构该收拢的信号——但那要看到真实数据才判断得了，所以本次不预先设计，
在 VISUAL DIFF 那一步用 2026 银组的真实名单看一眼。

## Referenced Capabilities

- `team-roster` —— 读路径的两处（球队列、名单页）在这里。本次改它的**数据来源**，
  响应的字段集合保持不变（`dutr_status` / `source_note` / `daily_utrs` 留在响应里但恒为
  null，见 Non-Goals），`is_borrowed_player` 改从成员关系读取。端点、路径与其余字段
  语义不变。
- `lineup-search` —— 名单读取与 key 格式在这里改；估算与未裁决两类标记要进它的响应。
- `lineup-ui` —— 上述两类标记的呈现，以及旧链接失效的提示。
- `player-registry` —— 新的数据来源。推导链读它的 `player_season_utrs` 与
  `players.doubles_utr`/`doubles_status`。
- `team-roster-ui` —— 名单页「UTR 来源」列的收缩，以及当前 UTR 那一列的说明文字。

## 探索阶段测得的事实

- **读取消费者只有三处**：`rosters/query.list_teams`、`rosters/query.get_team_roster`、
  `lineups/query.load_roster`。另外 `rosters/load.py`（导入器）与 `players/migrate.py`
  也碰 `roster_entries`，但那是写入与迁移，不在本次读路径范围内。
- **三个字段在新模型里没有对应物**：`dutr_status`（名单页正在显示）、`source_note`、
  `daily_utrs`。迁移当初只搬了判定结果，没搬原始凭据。
- **当前 UTR 现在一个都没有**：迁移的 `_create_player` 只写姓、名、性别、UTR 链接四个
  字段，组委会总表里根本没有当前 UTR 这一栏。线上 387 名队员的
  `singles_utr`/`doubles_utr` 全为空。所以推导链的第 2 步现在一个人都命中不了，
  实际生效的是第 3 步（去年 match UTR，375 人有值）。
- **今天缺口是零**：线上 489 条成员关系对应 405 条赛季 UTR，其中 2026 的 30 条成员关系
  每条都有 2026 的值。推导链是为往后准备的——admin 新建的人、总表更新前新入队的人。
- **阵容 key 现在是 `roster_entries.id`**：`load_roster` 里 `key=str(entry.id)`，锁定经
  query 参数往返，因此这个 id 出现在用户分享的 URL 里。
