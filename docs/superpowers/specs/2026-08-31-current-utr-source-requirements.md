# current-utr-source

给 `players.singles_utr` / `singles_status` / `doubles_utr` / `doubles_status` /
`utr_profile_id` 五个字段一条**入口**。后端 `PATCH /api/players/{id}` 早就能写它们，
迁移与名单 CSV 都不带这些数据，界面上也没有任何编辑口，所以线上 375 名队员的这五个
字段**一个都没有值**，名单页那两列一整列是 `—`。

直接后果：参赛 UTR 推导链的第二步（当前 `rated` 双打值）永远不命中，只能靠第三步
（最近一个有值赛季）接住。9/21–9/25 取样窗口之前，组委会的参赛 UTR 还没出来，
当前 UTR 是唯一能先估一估阵容的依据。

## Goals

- **按队的往返表**：系统导出一张已经带好 `id` 与姓名的表，人在 Google Sheets 里填
  UTR 那几列，再把整块贴回来或作为 CSV 传回来。
- **身份靠 id 往返，不靠匹配**。`players.id` 从我们这儿出去、原样回来，中间没有
  「这一行是谁」这个判断。姓名同行带回，只作**校验位**。
- **先看差异再落库**。粘贴/上传后先出一屏差异，确认后才写。
- **单人就地改**：名单页上直接改一个人的这几个字段，不必为补一个人走一趟往返。
- 第一次往返顺便把 `utr_profile_id` 收上来 —— 它不当匹配依据，只是让页面能跳到那个人
  的 UTR 档案。

## Non-Goals

- **不吃 UTR 官网的导出文件**。那条路要一整屏「候选 / 重名消歧 / 跳过 / 新建」的匹配
  确认界面，是本 change 的两倍多，且在拿到一份真实导出文件之前是凭空设计。记为
  backlog 的 `utr-export-ingest`。
- **不做与 UTR 官网的自动同步/抓取**。需要账号与登录，且是别人家的服务。
- **不动参赛 UTR**（`player_season_utrs`）。那是赛季冻结值，有自己的裁决与锁流程。
- **不做导入历史/审计表**。谁在什么时候改了什么，本次不留痕。
- **不改推导链**。链的四步不变，本 change 只是让第二步终于有数据可用。
- **移动端版式**。

## Constraints

- **架构**：浏览器只与 Next.js 通信；写入经 Server Action → `frontend/lib/admin.ts` →
  FastAPI，`lib/api.ts` 仍是读取的单一出口。不新增浏览器直连。
- **鉴权**：写入按 HTTP 方法在 `app/auth.py` 中间件里判定，新写路由不声明也已被保护。
  导出是读，与名单页同级。
- **无 schema 变更**：五个字段都已存在。本次不写 migration。
- **`Decimal` 全程**：UTR 值 10.25 与 10.2 是不同答案，任何一处退化成 float 都只在
  边界上错。
- **状态词汇是 `CURRENT_UTR_STATUSES = {unrated, projected, rated}`**（UTR 官网自己的
  词），与赛季那套 `{verified, committee, captain}` 是两个词汇表，不得互相映射。
  比对**大小写不敏感**（官网写 `Rated`，人手抄成 `rated` 都算），但只认这三个词；
  别的词不猜，整行拒绝。
- **赛季锁不拦这里**。`_assert_season_open` 守的是参赛 UTR；当前 UTR 是队员自己的属性，
  不属于任何赛季。
- **当前 UTR 是全局的，不按队也不按赛季**。同一个人同时在金银两组时（2025 有 17 人），
  从任一张表导进去的值，另一组的页面上看到的是同一个。

### 「空」的三种含义

填表这一步在系统外面，所以「这个格子没写东西」必须只有一个意思，否则第一次使用就会
误伤真实数据。

- **空白 = 不改**。最常见的用法是只填几个人，把空白当清空会在第一次导入时抹掉一整队。
- **清空要显式写记号**（如 `-`）。不给这条路，一个填错的值就再也回不到「没有」。
- **值与状态必须成对**。只给数字不给状态，等于给出一个推导链用不上、页面上却照常显示
  的数字 —— 看的人会以为它能用。只给一个时整行拒绝并说明缺哪个。
- **行数少于队里的人 = 其余不变**，但差异屏 SHALL 报出「本表覆盖 N 人，队里另外 M 人
  未包含」。停下太严（只填几个人是正常用法），不报则是静默。

## Success Criteria

- 从 2025 银组任一支队导出，表里每行带 `id` 与姓名，UTR 五列为空。
- 把该表原样贴回/传回，差异屏显示「0 处改动」——**往返本身不产生变化**。
- 填入若干值后贴回，差异屏逐行列出「谁的哪个字段从 `—` 变成什么」，确认后落库，
  名单页与队员详情页立刻可见。
- 空单元格不清空既有值；只填双打的一行不会把单打抹掉。
- 单元格写 `-` 时该字段被清回「没有」，且差异屏把它显示成一次改动而不是跳过。
- 只填了 UTR 值、没填状态的行被拒绝，报告指出缺的是状态。
- 表里只留 5 行贴回时，其余队员不变，差异屏写明「本表覆盖 5 人，另外 21 人未包含」。
- 状态列写 `Rated`（大小写不同）能被接受；写 `已认证` 整行被拒绝并说明原因。
- 行序被打乱、或某行姓名与 id 对不上时，**整批停下**并指出是哪几行，不落库。
- 表里出现库里没有的 `id`，同样整批停下。
- 导入涉及的队员若同时在另一组名单上，报告中点名说明。
- 名单页上改一个人的当前双打 UTR 并保存后，该队排阵页上此人的估算来源变为
  `估算 · 当前已认证值`（前提是他本赛季没有参赛 UTR 且状态为 `rated`）。
- 未登录时名单页看不到任何编辑入口，且直接调写接口被拒。

## User Stories

- 作为队长，我想把一支队的名单导成一张已经写好 id 和姓名的表，拿去 Google Sheets 里
  照着 UTR 官网填，填完整块贴回来，而不是在页面上一个个点开改 26 次。
- 作为队长，我想在真正写库之前看见「这次会改谁的什么」，因为填表那一步在系统外面，
  最容易犯的错是整列错位，那种错写完之后就没有原值可对了。
- 作为队长，临时补一个人的 UTR 时，我想直接在名单页上改，不必为一个人走一趟往返。
- 作为队长，我想知道我这次改的人里有哪几个同时也在另一组的名单上 —— 否则我会以为
  自己只动了这一组。

## 视觉决定（已定稿，见 mocks）

- **差异屏按人分组**，不是逐字段表格。一人一行，该人的三个字段挤在一行里。
  代价是列不对齐、看不出「一竖排全在变」，因此顶部补一行**按字段的改动计数**：
  只想填 3 个人的双打却看到「单打 12 处」，就是粘错列了。
- **有任何一行被拒绝，整批不写**，确认按钮禁用。整列错位时几乎每行都会被拒，
  放行一半只会让库里一半新一半旧。
- **「不变」的字段占位显示**，不省略 —— 省掉之后满屏都是变动，反而看不出
  「这个人我只动了双打」。
- **跨组的人点名**：顶部一条 warning 加行内标记。
- **导出与导入是同一屏的两个 tab**；导出三列灰底表示「别改」；导入按钮写「看差异」
  而不是「导入」，明确它不写库。
- **就地编辑整行变输入框**，一次一个人，不做同屏改多人 —— 那正是批量导入要解决的事，
  两条路做同一件事只会让人不知道该用哪条。
- **路由**：`/[season]/[division]/teams/[code]/utr`。离名单最近，代价是要给这条路由
  自己配一个登录门（照 `players/layout.tsx` 的做法）与 `error.tsx`。
- **未登录时**名单页不出现「改」与「批量导入」两个入口，页面照常只读。
- **不出移动稿**：四屏都是表格与表单，随既有响应式布局回流；`mobile-shell` 是单独
  一个 change。

## Open Questions

- **「UTR链接」列填什么**：完整链接还是纯数字 ID？倾向两种都接受，存库时归一成
  `utr_profile_id`。需要确认 UTR 档案链接的实际形态（有无查询串、会不会带用户名）。
  不阻塞实现 —— 先按「都接受」写，拿到真实链接再收紧。

- `player-admin-ui` —— 已有的登录门、管理员写入的 Server Action 形态、错误态与

## 探索阶段测得的事实

- `PATCH /api/players/{id}`（`PlayerPatch`）已接受全部五个字段；`PlayerIn` 亦然。
  缺的只是入口。
- `frontend/app/[season]/[division]/players/[id]/page.tsx` **只读展示**这些字段
  （第 123–136 行），没有编辑表单。
- `app/players/migrate.py` 的 `_create_player` 只写 `last_name` / `first_name` /
  `gender` / `utr_profile_id`；而 `utr_profile_id` 取自 `roster_entries.utr_profile_id`,
  那一列是手工维护的，总表里没有，所以实际全为空。
- 名单 CSV 的解析器（`app/rosters/parse.py`）没有任何当前 UTR 相关的列。
- 本项目已有四个导入器（规则 / 名单 / 队名 / 队员迁移），一律是
  「解析 → 读库 → 比对 → 只写差异」并配 `--check`。本 change 的两步流程是这套纪律的
  界面版本。
