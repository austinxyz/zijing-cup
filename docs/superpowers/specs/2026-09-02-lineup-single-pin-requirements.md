# lineup-single-pin

排阵现在只能**锁整对**（一条线两个座位都填）。队长常常只想「把某个人钉在某条线，搭档
交给引擎」——每条线指定一个人，引擎在满足所有规则下配搭档、排满其余。当前 UI 里这么填
（一条线只选一个人）会被**无声丢弃**（半填的线不算约束），于是引擎忽略他的意图、给出一份
没照他钉法来的阵容，读起来像「系统算不出合适阵容」。本次补上单座位 **pin**。

触发这次的真实报告：2026 银组 ZJU-USC，队长每条线指定一个人（D1 Ye Ming、D2 Ma Xiaoyu、
D3 Ouyang Yubo、MD Zhang Guang、WD Shen Jiayi），系统给不出他要的阵容——查明不是计算错，
是这个功能根本不存在。

## 背景（探索阶段读到的事实）

- 前端 `constraintsFromQuery`：一条线**两个座位都填**才算锁定（`if (first && second &&
  first !== second)`），半填的线被丢弃。
- 后端 `_parse_locks`：`lock=LINE:keyA,keyB` 要求正好两个 key。引擎 `search_lineups` 的
  `locks: dict[str, Pair]` 是整对；锁定线 `options[code]=[那一对]`，两名被锁的人从
  `available` 里剔除，其余线看不到他们。
- 引擎主体是分支限界：`options[code]` 是每条线的候选对，递归每条线选一个，用一个 used 集
  保证不重用人。**pin 天然落进这套**：pin 那条线的 `options` = 「所有含被钉者的合法对」，
  被钉者从其它线的池子剔除（搭档仍从池子里现选），其余照旧。
- 无解诊断 `diagnose_line`（上个 change A）按四类原因（性别人手不足 / 都超 cap / 都超差距 /
  资格）分析一条线的候选池，但它**不知道 pin**——pin 造成的无解它会给出误导或空的原因。

## Goals

- **单座位 pin**：一条线只指定一个人 = 把他钉在这条线，引擎在满足全部规则（cap、全队
  buffer、搭档差距、男双不倒挂、高 UTR 人数与线位、性别组合）下选搭档并排满其余线，目标
  仍是上场十人参赛 UTR 之和最大。
- **半填即 pin，不再无声丢弃**：填一个座位就是一个 pin（取代现在「半填=忽略」）。两个座位
  都填仍是**硬锁整对**（现有行为不变）。pin / 硬锁 / 排除 可任意组合。
- **诊断懂 pin**：被钉的线配不出合法搭档而无解时，据实说明「你把 X 钉在 L，但 X 在 L 配不出
  合法搭档」，并复用 A 的四类原因——但**限定在「含 X 的对」**里算，而不是整条线的池子。
- 前端把「已钉一人、搭档交给引擎」这个状态显式呈现出来，不让它和硬锁或空线混淆。

## Non-Goals

- **不改硬锁整对的行为**（两个座位都填照旧）。
- **不做「钉在任意线、由引擎选哪条线」**：pin 绑定到**具体某条线**。跨线自动分配不在本次。
- **不改搜索目标函数、cap/buffer/资格规则本身、候选呈现（对比表/紧凑行）**。
- **不做保存 pin 组合**（那属于 lineup-saved-filters 的 preset：preset 存的是这批 query
  参数，pin 一旦编码进 query 就自然可被 preset 存下——但本次不动 preset 代码）。
- 不做 per-user / 存储 / 迁移。

## Constraints

### 架构

- 后端诊断只读候选池，MUST NOT 触发第二次整解搜索（沿用既有纪律）。
- 前端经 `lib/api.ts` 单一出口取数；pin 编码进 URL query（与锁定/排除同为可分享的地址）。
- 无新表、无 migration。

### 语义 / 正确性

- pin 是「被钉者 MUST 出现在该线」。引擎 SHALL 只在**含被钉者的合法对**里为该线选搭档，
  且被钉者 MUST NOT 出现在其它线。硬锁（整对）语义不变。
- **一条线的档位判定按已填座位数**：填**恰好一个**座位（哪个座位都行，座位无序）= pin；
  两个都填 = 硬锁整对；都不填 = 交给引擎。同一条线两个座位填了同一个人 SHALL 被拒
  （既非合法对也非合法 pin）。
- 一条线最多一个 pin；同一条线两个座位都填即升级为硬锁，不是「两个 pin」。
- 一个人 MUST NOT 被同时钉到两条线（同一人多处 = 非法输入，明确拒绝，别静默取一个）。
- **pin 与排除互斥**：被钉的人 MUST NOT 同时出现在排除名单里（一个说必须上、一个说不能上，
  是矛盾输入）→ 明确拒绝，别静默偏向其一。同理被钉者也不应同时是某条硬锁线的成员。
- pin 与硬锁引用的人一律走**与手填 URL 完全相同**的后端校验（未知 key → 4xx、旧格式 key →
  stale-link）。pin MUST NOT 成为新的信任入口。
- 被钉者可以是女将钉在男双线（女性可填男双座位，既有规则允许）；MD 的 pin 若是男，搭档
  MUST 是女，反之亦然；WD 的 pin MUST 是女。这些由既有 `legal_pairs` 的性别判定负责，
  pin 只约束成员身份。
- 诊断的 pin 感知：pin 那条线无解时，`diagnose_line` SHALL 在「含被钉者的对」范围内给原因，
  MUST NOT 报出与 pin 无关、看起来「本可行」的原因。

### 呈现

- 被钉的线（只填一个座位）SHALL 有明确视觉标识（如「已钉 · 搭档交给引擎」），与硬锁（两个
  座位）和空线（交给引擎）区分开。
- pin 造成无解时，无解面板 SHALL 点名被钉者与线，复用既有样式档与对比度纪律（≥4.5:1、桌面与
  <768 都读得清、不横向溢出）。
- 数值一律用后端字符串，前端 MUST NOT 拿显示值做比较。

### 测试

- 后端 pytest：pin 单线（引擎配出合法搭档）、多线 pin 联合可解、pin 造成无解且诊断限定在
  含被钉者的对、同一人钉两线被拒、女将钉男双、pin+硬锁+排除组合。
- 前端 vitest + `npx tsc --noEmit` 单列。
- 本地看页面前不跑 pytest（会清库）；顺序：先测试 → 补种 → 视觉核对。

## Success Criteria

1. 每条线指定一个人（如报告里那套 ZJU-USC）→ 引擎给出一份把这些人各自钉在指定线、其余
   合法排满、总和最大的阵容；不再无声丢弃。
2. 两个座位都填仍是硬锁整对，行为与改动前一致；pin/硬锁/排除可混用。
3. 被钉者只出现在被钉的线；一个人钉两条线的输入被明确拒绝。
4. pin 使某线无解时，诊断点名被钉者与线、并在「含被钉者的对」里给出四类原因之一，不给
   与 pin 无关的误导原因。
5. pin 编码进可分享的 URL，直接访问该 URL 得到同一套约束，走与手填相同的后端校验。
6. 前端把「已钉一人·搭档交给引擎」显式呈现；桌面与 375 都读得清、0 对比度不合格、无横向溢出。
7. `npx tsc --noEmit` 干净；vitest 与 pytest 全绿。

## User Stories

- 作为队长，我想把主力一号钉在 D1、某个混双好手钉在 MD，其余交给引擎，一次算出满足这些
  钉法的最强阵容，而不用自己手配十个人。
- 作为队长，我每条线只点一个人时，系统就该按我点的来排，而不是当我没点。
- 作为队长，如果我把某个人钉在一条他其实配不出合法搭档的线上，我要它直接告诉我是这个钉法
  的问题、卡在哪一条规则，而不是给我一份没照我来的阵容或一句空话。

## Open Questions

1. URL/后端编码：新参数 `pin=LINE:key`（与整对 `lock=LINE:keyA,keyB` 并列），还是让
   `lock=LINE:key`（单 key）表示 pin？—— design 定（倾向独立 `pin=`，不重载 lock 解析）。
2. `diagnose_line` 怎么接收 pin：多传一个 `pinned: dict[line,key]` 参数，在含被钉者的对里
   跑同一套四关分类？—— design 敲定签名。
3. 引擎里 pin 的实现细节：`options[L]` = 过滤 `legal_pairs` 到含 pin 的对；pin 从其它线
   `available` 剔除、搭档不剔除——确认递归 used 集与「scarcest first」排序不被破坏。—— design。
4. 被钉一人、搭档交给引擎 在控件里的视觉呈现（半填态的标识、窄视口抽屉里的排布）。—— Phase 4。
