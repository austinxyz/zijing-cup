# lineup-results-redesign

排阵页的候选阵容现在是 20 张叠卡，每卡把五线（D1/D2/D3/MD/WD）塞进五个 `flex-1`
窄列，一对搭配「name男 + name男」在窄列里换行成 ~116px 高、整卡 ~177px，20 套叠起来
是一条 ~3500px 的长滚动。负责人的原话：**太挤，翻阅很不方便**。

用法是「**快速扫、挑一套**」。而 Top 几套常常总和相同（结果页顶部的 `squads_at_ceiling`
就是「顶点有多少套」），同分时真正用来挑的是**具体搭配（谁配谁）与某几个关键人的位置**
—— 所以搭配不能藏起来，得让它可扫、可对齐比。

本次是**纯前端重排**：不动后端、不动搜索、不新增数据。`LineupCandidate` 的字段
（`total` / `buffer_spent` / `lines` / `line_totals`）已经够用。

## Goals

- **桌面：候选从叠卡改成一张对比表。** 行 = 候选（后端 `keep=20`，至多 20 行），
  列 = 名次 / 总和 / buffer + 五线（D1/D2/D3/MD/WD）。列对齐、名字**不换行**，
  竖着扫一列就能看「谁在 D1」，某个关键人落在哪套哪线一眼可见。
- **手机：候选是紧凑行，点开看详情。** 每套默认一行（名次 + 总和 + 一条签名），
  点开展开五线**纵向堆叠**、名字不换行。扫总和/签名，开有戴的那套。
- **不丢任何既有的合法性信号**：估算值、超 cap、buffer 用量、未裁决/缺 UTR 提示。
- 缓解「挤」（名字不再在窄列里换行）与「翻阅不便」（桌面可竖扫对齐、手机紧凑）。

## Non-Goals

- **不做「关键人高亮」**（点一个名字、所有候选里高亮他）。它直接服务「关键人位置」，
  但要加交互与客户端状态，本次先不做，后续单列。**注意区别**：对比表让「关键人位置」
  可见靠的是**列对齐 + 竖扫**（人眼自己找），不是任何高亮/筛选交互 —— 表是静态的，
  「一眼可见」指的是对齐后好扫，不是系统替你标出来。
- **不动顶部摘要区**（可达上限 / 规则允许 / 差值 / 同分组数 / 锁定代价 / 未裁决与缺 UTR
  的顶部提示）。负责人只说候选挤、难翻，摘要不在抱怨范围。
- **不动后端 / 搜索 / 排序 / 去重 / `keep=20`**。前端 MUST NOT 自行重排候选 —— 后端已按
  总和从高到低、同分常见，二次排序每次渲染会挑出不同的赢家（既有约束，保留）。
- 不做无解 / 非法锁定 / 截断这些非正常态的重排 —— 它们已是各自的面板，只改**有候选**
  时的候选呈现。
- 不做导出 / 分享 / 收藏某套阵容。

## Constraints

### 架构

- 纯前端，改的是 `LineupResults`（与拆出的候选呈现组件）。取数仍走既有路径。
- 不新增运行时依赖。

### 既有不变式（从当前实现继承，测试已覆盖，MUST 保留）

- **前端不重排候选**：按后端给的顺序渲染（同分是常态，二次排序会漂移）。
- **估算值标两处**：某数字来自推导值时数字旁标（当前是「估算」badge），且整套含估算时
  标一次「含 N 个估算值，合法性待总表确认」—— 合法性是整套的属性，一个估算值让「这套
  合法」本身成为估算。两处都不能只剩一处。
- **超 cap 就地标**：某线之和超过该线 cap 时标「超 N」。
- **buffer 用量**成对显示：`buffer_spent / buffer_total`，两侧同两位小数（`0/0.50` 与
  `0.21/0.50` 要读成同一种数）。仅显示，一切比较在后端。
- **数值全程按后端给的字符串显示**，前端 MUST NOT 拿显示值做比较（cap 判定在后端，
  `10.25` 与 `10.2` 是不同答案）。
- **性别**跟着每个名字显示 —— 高 UTR 人数上限按性别写，缺了性别就没法肉眼核对。
- 开放线（cap 为 null）显示「无上限」而非一个编造的数字。

### 断点

- < 768px 走手机紧凑行；≥ 768px 走桌面对比表。沿用 mobile-shell 的 `md` 断点，
  不引入新断点。

### 高度与滚动（沿用 mobile-shell 的地基）

- 壳是 `h-[100dvh]` / `overflow-hidden`（`shell-height`）。对比表与紧凑列表**必须自带
  滚动容器**，否则长列表被静默裁掉且不出滚动条。桌面对比表的**表头要在滚动时钉住**
  （否则 20 行滚下去就不知道哪列是哪线）。
- 桌面对比表**横向不溢出视口**：五线 + 三个元信息列要在常见桌面宽度（≥768，实测到
  1280）内放得下；名字长时列内截断或换用短形，而不是把整表推宽出横向滚动条。

### 对比度（沿用 mobile-shell 的纪律）

- 所有文案 ≥ 4.5:1，量 computed style 而非照源码估。新做的表格 / 行显式给
  `bg-surface`，不靠继承页面底色（`--color-muted` 在页面底色上 4.27、在白底 4.97）。
- 估算 / 超 cap 的 warning 档沿用既有 token（`--color-warning*`），不新增颜色对；
  若要硬编码颜色对，配一条针对性对比度断言（SETTLED badge 3.68 的教训）。

### 测试

- `npm run test`（vitest）不做类型检查，`npx tsc --noEmit` 单列。
- 视觉核对量最长数据：`keep=20` 的满 20 套 + 26 人名单的队（如 USTC-CMU-HQU），
  桌面 1280 与手机 375×667 各核一遍。
- 本地看页面前不要跑 pytest（会清库）；顺序：先测试 → 补种 → 再视觉核对。

## Success Criteria

1. 桌面（≥768px）候选呈现为一张表：每套一行，列含名次、总和、buffer、D1、D2、D3、
   MD、WD；同一列跨行对齐，可竖扫「谁在这条线」。
2. 满 20 套 + 26 人队时，桌面表**无横向溢出**，名字不换行（长名截断而非撑宽表），
   表头滚动时钉住，表体可滚到第 20 行。
3. 手机（375px）候选为紧凑行：名次 + 总和 + 一条签名；点开展开五线纵向堆叠、名字
   不换行；关上回到列表。无横向溢出。
4. 估算值：某数字为推导值时其旁有估算标记；整套含估算时有「含 N 个估算值……」整套标记。
   两处都在（桌面表与手机展开态都要有）。
5. 超 cap 的线就地显示「超 N」；buffer 显示 `spent/total` 两位小数。
6. 顶部摘要区（可达上限 / 规则允许 / 差值 / 同分组数 / 锁定代价 / 未裁决 / 缺 UTR）
   与改动前一致。
7. 前端不重排候选：给定同一份后端响应，渲染顺序与 `search.candidates` 一致。
8. 全站相关页对比度 ≥ 4.5:1（桌面 + 手机双跑，0 不合格）。
9. 无解 / 非法锁定 / 截断等非正常态与改动前一致。
10. `npx tsc --noEmit` 干净；vitest 与 pytest 全绿（本次预期不动后端测试）。

## User Stories

- 作为队长，我想一眼扫过 20 套候选、竖着看「谁被排在 D1」，而不是在 20 张各自为政、
  名字挤到换行的卡片之间来回找。
- 作为队长，几套总和一样时，我想快速比出它们的搭配差在哪、我那几个主力被摆在哪条线。
- 作为队长，比赛当天在手机上，我想扫一列总和、点开看着顺眼的那两套的完整五线，而不是
  滚过一条 3500px 的长卡带。
- 作为队长，我仍要一眼看出哪套含估算值、哪条线超了 cap —— 这些不能因为版式变了就没了。

## Open Questions

1. 手机紧凑行的**签名**放什么？候选：D1 搭配 / 代价标记（含估算·超cap）/ 两者混合。
   —— Phase 4 视觉稿定。
2. 桌面表里**长名**怎么处理：截断 + hover 全名 / 缩短（姓+名首字）/ 换行只此一列。
   —— Phase 4 视觉稿定。
3. 估算 / 超 cap 在**表格格子**里的标法：图标 / 角标 / 底色 —— 既要就地可见又不能把
   格子撑高破坏对齐。Phase 4 视觉稿定。
4. 桌面表是否保留每套的「含 N 个估算值」整套提示行（表里一行占位 vs 行内一个整行标记）。
   Phase 4 视觉稿定。

## Referenced Capabilities

- `lineup-ui` —— 本次修改的能力。当前 `LineupResults` / `CandidateCard` 的候选呈现被
  对比表 + 紧凑行取代；顶部摘要区与非正常态面板不变。mobile-shell 刚给排阵页加的
  结果打底 + 约束抽屉不受影响（约束抽屉是控件侧，本次改的是结果侧）。

## 探索阶段测得的事实

- 后端 `app/lineups/search.py` 的 `keep: int = 20` —— 候选至多 20 套。
- `LineupCandidate`：`total` / `buffer_spent` / `lines`(5×[player,player]) /
  `line_totals`(每线 total + over)。无候选级唯一 id、无区分标签 —— 区分只能靠搭配。
- `LineupPlayer`：`key` / `last_name` / `first_name` / `gender` / `match_utr` /
  `origin`(frozen|current_doubles|prior_season) / `origin_year` / `is_unresolved`。
- 当前 `CandidateCard`：96px 总和列 + 五个 `flex-1` 线列；实测每卡 ~177px，
  一对搭配窄列内换行 ~116px 高。
- 顶部摘要区、未裁决/缺 UTR 提示、无解/非法锁定/截断面板都在 `LineupResults` 里，
  本次只换「有候选」时的候选列表部分。
