# lineup-saved-lineups

排阵能搜出候选阵容、能存过滤条件（B）、能钉人（pin），但**选定的那一套阵容留不住**。
队长挑好一套想收着，过些天参赛 UTR 动了（赛季未锁时改当前 UTR 会覆盖参赛 UTR），这套阵容
可能已经不合法了，但他无从知道。本次：**保存一套具体阵容 + 当前参赛 UTR 快照**，之后在一个
**专门的已存阵容页**里重判合法性、点名哪些人的 UTR 动了；并允许在该页**就地编辑**（线间互换、
从名单替人）修好失效的阵容，每次改实时判合法性。

这是三条阵容增强里的 C（A infeasibility-detail、B saved-filters 已落地）。用户选择 C1（存+失效
标记+看）与 C2（就地编辑器）**合并为一个 change** 做完。

## 背景（探索阶段读到的事实）

- 合法性是整套阵容的属性，由 `rules.py` 的 `check_lineup(rules, lineup) -> LegalityReport`
  判定：`lineup` = `{线: (CandidateA, CandidateB)}`，返回 `violations`（超 cap / 全队 buffer /
  搭档差距 / 男双倒挂 / 重复上场 / 资格）。**重判与编辑器实时判都复用这一个函数。**
- 合法性算的是**参赛 UTR**（`match_utr`）。它会变：赛季**未锁**时改当前双打 UTR 会覆盖该赛季
  参赛 UTR（既有机制）；或组委会重新导入。赛季**锁**后冻结——锁后快照恒等于当前。
- 候选阵容 = 5 线 × 2 人，结果区已按对比表/紧凑行呈现（`lineup-results-redesign`）。保存入口
  挂在候选行上。
- 队员 key 是队专属的 `p<id>`；旧格式 key 有 stale-link 处理。存储沿用 B/preset 的模式：
  `zijing_cup` 新表、admin-global、按 (赛季,组别,队)、写路由靠 HTTP 方法自动受保护。
- 前端无法自己判合法性（cap/buffer/资格逻辑在后端）；重判与编辑实时判都要走后端。

## Goals

- **保存一套阵容**：候选结果行上「保存此阵容」→ 存这套 10 人的**线位分配** + 当前每人参赛 UTR
  **快照**（admin、命名、按队；名唯一、同名覆盖）。
- **专页重判**：一个已存阵容页列出该队所有已存阵容，每套**服务端**用**当前**参赛 UTR 重跑
  `check_lineup`，给状态：仍合法 / UTR 动了但仍合法 / **已非法**（点名卡哪条约束）/ 有人已不在
  名单。并逐人点名**快照 vs 当前**的 UTR 差异（陈嘉禾 6.5→7.0）。
- **就地编辑**：在该页把一套阵容改一改——**线间互换**两人、从名单**替换**个别人——修好失效的。
  **每次改实时重判**（后端 `check_lineup` 打当前 UTR，告诉卡哪条）。
- **存回 / 载入 / 删除**：编辑后存回（覆盖 + 重拍 UTR 快照）；一键**载入**（把这套锁满五线写进
  排阵页 URL，用当前 UTR 重新展示/继续搜）；admin 删除。

## Non-Goals

- **不改搜索引擎、目标函数、cap/buffer/资格规则、候选呈现、pin、B/preset 代码**（保存阵容与
  保存过滤是两个独立存储）。
- **不做自动修复**：失效阵容由用户手动互换/替人修，系统只实时说合法与否、卡哪条，不替他找方案。
- **不做 per-user / 归属 / 多租户**：admin-global。**不冻结 / 不改任何人的参赛 UTR**——快照只是
  存下当时的值供对比，不回写、不影响排阵的真实取数。
- **不做跨队/跨组别共享**（key 队专属）。**不做历史版本**（存回即覆盖，不留旧版）。

## Constraints

### 架构

- `zijing_cup` 新表、新 migration（`set search_path to zijing_cup, public;`）。远程共享 Supabase
  **不跑 CLI push**，去 Dashboard SQL 手动执行；本地打本地栈（断言连接串含 `127.0.0.1`）。
- 存的是**输入形状**：线位分配 `{线:[keyA,keyB]}` + UTR 快照 `{key: "match_utr 字符串"}`，
  最自然一列或两列 JSONB。—— design 定列形。
- 重判与编辑实时判**复用 `check_lineup`**，MUST NOT 复制一份合法性逻辑。校验一套 assignment 的
  只读端点接收 5 线 × 2 key，用当前 `match_utr` 解析成 `Candidate` 后跑 `check_lineup`，回
  violations（结构化、带中文 message，复用既有 `Violation`）。
- 前端经 `lib/api.ts`（读 + 校验）与 `lib/admin.ts`（存/删/存回）取数；浏览器不碰后端地址/密钥。
- 写路由靠 **HTTP 方法**自动受保护，MUST NOT 靠路由前缀或依赖式鉴权。

### 真实性 / 安全

- 快照**只读留存**，MUST NOT 回写参赛 UTR、MUST NOT 影响排阵引擎的真实取数——它只用于「当时是
  多少 vs 现在是多少」的对比。重判永远用**当前**值。
- 存/编辑引用的 key 走**与手填 URL 完全相同**的后端校验（未知 key → 4xx、旧格式 → stale-link）。
- 有人已不在名单（key 解析不到当前 `match_utr`）→ 该套阵容标「有人离队」，不静默丢人、不假装合法。
  **载入**一套含离队/旧格式 key 的阵容，沿用 B 的 stale-link 处理（不发带坏 key 的搜索、明说重建）。
- **编辑是自由改，合法性是唯一护栏**：替换从整队名单里挑（含已在阵容里的人 → 会造成重复上场），
  系统 MUST NOT 预先禁止，而是靠实时 `check_lineup` 当场报出（重复上场是它的一条 violation）。
  互换是选两个槽对调。系统只据实说合法/卡哪条，不替用户拦、不自动修。
- **重判（看）是 GET、开放**；**校验一套 assignment（编辑实时）是 POST**（body 带 5 线 assignment），
  因而被**方法判权中间件自动要求 admin**——这与「编辑是 admin 动作」正好一致，非 admin 只看不编。
  MUST NOT 为了绕开而把校验做成开放的写路径。
- 名字是 admin 手填文本，参数化入库、前端转义；名长 + 每队数量上限（防滥用）。—— design 定值。

### 呈现

- 已存阵容页沿用既有样式档、显式给底色，对比度 ≥ 4.5:1（实测 computed style），桌面与 <768 都
  读得清、不横向溢出、触摸目标 ≥44px。状态分档用色：合法（中性/success）、UTR 动了仍合法
  （中性提示）、已非法（warning/danger 点名卡哪条）、有人离队（warning）。
- 编辑器的互换/替换要有清楚的选择反馈；实时合法性结果就近呈现（哪条线红、总量超多少）。
- 数值一律用后端字符串，前端 MUST NOT 拿显示值做比较。

### 测试

- 后端 pytest：存/取/删/同名覆盖、UTR 快照留存不回写、重判四态（合法/动了仍合法/已非法/离队）、
  校验端点对合法与各类非法 assignment 的 violations、编辑存回覆盖 + 重拍快照、无 admin 凭据写被拒。
- 前端 vitest + `npx tsc --noEmit` 单列。
- 本地看页面前不跑 pytest（会清库）；顺序：先测试 → 补种 → 视觉核对。

## Success Criteria

1. 从候选行保存一套阵容 → 已存阵容页列出它，带名字、10 人线位、保存时 UTR 快照。
2. 某队员参赛 UTR 在保存后变化 → 该页点名「谁 从 X 到 Y」，并用**当前**值重判：仍合法就标仍合法，
   变非法就点名卡哪条约束（超 cap 多少 / 超 buffer / 超差距 / 资格）。
3. 有人已不在名单 → 该套阵容标「有人离队」，不呈现为合法。
4. 在已存阵容页就地**线间互换**两人或**从名单替换**一个人，**每次改实时**看到合法性结果（合法 /
   卡哪条）；存回后覆盖原阵容并重拍 UTR 快照。
5. 一键**载入**把该套锁满五线写进排阵页 URL，用当前 UTR 重新展示（合法出这套、非法走 invalid_locks/
   无解面板）。
6. 无 admin 凭据的存/删/存回被拒（方法判权）。快照绝不回写真实参赛 UTR。
7. 桌面与 375 都读得清、0 对比度不合格、无横向溢出；`npx tsc --noEmit` 干净；vitest 与 pytest 全绿。

## User Stories

- 作为队长，我搜出一套满意阵容，想存着，别每次重排；过几天有人 UTR 涨了，我要一眼看出这套还合不
  合法、是谁把它顶超了。
- 作为队长，某套阵容失效了，我想在页面上把 D2、D3 两个人对调一下，或把某个人换成名单里另一个，
  当场看到改完合不合法，合法了就存回去。
- 作为队长，我要它只据实说「合法/卡哪条」，不替我瞎改、也别偷偷拿旧 UTR 糊弄我说还合法。

## Open Questions

1. 存储列形：线位分配 + UTR 快照放一列合并 JSONB 还是两列？—— design 定（倾向两列，语义分明）。
2. 校验端点形状：`POST /.../validate`（body 是 5 线 assignment）回 violations？还是复用现有搜索端点
   的某种模式？编辑器每次改一次请求，注意冷启动延迟——是否需要前端节流/乐观。—— design。
3. 已存阵容页的路由：`/[season]/[division]/lineups`（列表）+ 就地编辑，还是列表页 + 单套编辑子路由？
   —— Phase 4 视觉稿定。
4. 编辑器的互换/替换交互（选中两个槽互换？下拉替换？）、实时合法性结果的就近呈现方式、窄视口排布。
   —— Phase 4 视觉稿。
5. 每队已存阵容数量上限、名长上限。—— design。
