# notes-surfacing — 把球员评价展示到排阵/对手对比/roster（展示 + 轻提示）

已有的球员评价（`player-notes`，挂在人上、跨赛季、机密）目前只在队员详情右栏可见。本 change 把它
**只读地**呈现到三个做决策的界面——排阵页候选、对手对比逐线、队伍 roster——让队长在排阵当下一眼看到
「这人有记优点/弱点/搭档」，并能悬停/点开读全文。**展示 + 轻提示**：弱点用警示色、优点用正色一眼可辨，
但**不改引擎、不改合法性判定、不改推荐排序**。

## Goals

1. **三处只读展示评价。** 排阵页（候选卡 + 已存阵容）、对手对比两侧逐线的每对球员、队伍 roster 每行，
   旁边显示该球员的评价信号。这三处**只读**——追加/删除仍只在球员详情页；这里是决策界面不是编辑界面。
2. **同一份数据、两种密度展示。** 空间不同 → 标记形态不同，但点/悬停都开**同一个**倒序时间线弹层
   （类别中文标签 + 文本 + 时间，只读）；没有评价的球员不显示任何标记（不占位、不留空标记）：
   - **roster / 对手对比**（每行一人，宽）：整组**分类小标**（优点 ● 正色 / 弱点 ▲ 警示色 / 搭档 ◆ 蓝 /
     其他 灰），一眼看到「有记弱点」。
   - **排阵 seat**（候选卡 + 已存阵容，经**共享 `LineBlock`**，极窄、已有 外/▲/估 三个内联标记）：
     一个**单标记「评」**，与既有内联标记同族；**含弱点时用警示色**，否则中性色。类别在弹层里看。
   - **一个接入点覆盖两块**：候选与已存阵容都走 `LineBlock` 的 seat，改这一处两块同时生效、读起来一致。
3. **轻提示 = 类别存在性信号，不是精确匹配。** 因为「搭档」类别是自由文本（无结构化球员引用），
   MUST NOT 声称「你排进来的正是推荐搭档」这种自动匹配。信号只表达「此人有某类评价存在」，判断留给人。
4. **机密门，与详情页一致。** 三处都按 `canEdit(season, division)` gate：未解锁本比赛者不取、不显示任何
   评价内容与小标。对手对比**两侧都显示**（看对手评价正是侦查目的；对手球员同属本组，解锁本组即可见）。
5. **批量取数，一次往返。** 一个界面上 10–16 名球员，MUST NOT 每人一次 `getPlayerNotes`（N 次往返、
   冷启动叠加超时）。用一个按 player id 列表批量取的读端点，一次拿回按 id 分组的评价。
6. **取数失败降级，不拖垮宿主页。** 评价是只读旁支：批量取数任何失败 SHALL 降级为「无评价」（不显示小标），
   排阵/对比/roster 主功能照常——与 `getPlayerNotes`/`getTeamPresets` 同款降级。

## Non-Goals

- 不在这三处做写操作（追加/编辑/删除仍只在球员详情页）。
- 不做精确「推荐搭档已排入」匹配（搭档是自由文本，无结构化引用）。
- 不改排阵引擎、合法性判定、候选排序、推荐、打分——纯视觉信号。
- 不改 `player-notes` 的数据模型、机密语义、写路径。
- 不做跨球员的评价聚合/检索/筛选/统计。
- v1 不做「按类别过滤只看弱点」之类的界面控制（先把展示做好）。

## Constraints

- 架构不可违反：读经 `lib/api.ts` 单一出口、只有后端连库；浏览器不接触后端凭据。
- 复用既有 `PlayerNote` 模型/表，**不新增表、无 migration**（只加一个批量读端点 + 前端展示）。
- 机密门在前端 fetch 决策（仅 canEdit 时取），与详情页现有做法一致；批量读端点本身走 backend secret（读）。
- 三处的球员身份来源不同，需各自确认拿得到 `player_id` 作 key（已核对，见「已解决」）：
  - roster：`RosterPlayer` 带 `player_id` ✓。
  - 排阵候选/已存/对手对比：seat 数据经 `LineupCandidate`/`LineupPlayer`，`key=f"{PREFIX}{player.id}"`——
    给 `LineSeat`（及其上游 `LineupPlayer`/`LineupCandidate` seat）加一个 `player_id` 字段传下来。
- 展示组件分两个：`PlayerNotesBadges`（roster/compare 的完整分类小标）与 seat 里的单标记「评」；
  **两者共用同一个弹层组件**（`NotesPopover`/时间线）与同一份类别标签/颜色 token，避免漂移。
  排阵两块（候选 + 已存）的单标记只在 `LineBlock` 的 seat 加一处。
- 深浅色 + 对比度：小标与弹层文字对比度 ≥ 4.5:1；容器要显式给底色（见 CLAUDE.md 硬编码颜色/继承底色的坑）。
- 移动端：悬停不可用，改点开；弹层不能撑破 `h-screen overflow-hidden` 壳，自带滚动。

## Success Criteria

1. 解锁本比赛后：roster / 对手对比两侧对有评价的球员显示**分类小标**；排阵候选卡与已存阵容的 seat
   显示**单标记「评」**（含弱点时警示色）；无评价者三处都不显示任何标记。
2. 三处的标记点/悬停都弹出**同一个**倒序时间线弹层（类别中文标签 + 文本 + 时间），只读。
3. 弱点信号用警示色（小标 ▲ 与 seat「评」都是），优点正色；纯展示，不影响任何合法性/排序/推荐。
   排阵改动只在共享 `LineBlock` 一处，候选卡与已存阵容同时生效、读起来一致。
4. 未解锁本比赛的会话：三处都不显示任何评价内容、不发批量取评价请求。
5. 一个界面所有球员的评价用**一次**批量请求取回；批量取数失败时降级为「无评价」、主功能不受影响。
6. 本地真实数据 e2e：给几名球员记不同类别评价 → 三处都出现对应小标、悬停/点开读到全文；未解锁看不到、不请求。
7. 前端 vitest + `npx tsc --noEmit` 全绿；新源码无 console.log；小标/弹层对比度 ≥ 4.5:1。

## User Stories

- 作为队长，排阵时我想在候选球员旁看到他有「弱点：反手薄弱」的记录，好决定把他放哪条线、配谁。
- 作为队长，对手对比时我想看到对手某人记着「适合搭档某某」，据此预判他们会怎么配对。
- 作为队长，翻队伍 roster 时我想快速扫到哪些人有评价、点开读，不必逐个进详情页。
- 作为只读访问者（未解锁），我看不到任何评价——它是机密。

## Open Questions

1. 弹层交互：桌面悬停 vs 点击？移动统一点开。悬停弹层的可访问性（键盘/触屏）如何兜底——建议桌面
   悬停+点击都触发，移动点击。（mock 阶段定）
2. 小标形态：彩色圆点 + 类别，还是「类别字 + 计数」？是否显示条数（如 弱点×2）？（mock 阶段定）

### 已解决（代码核对）

- **球员 id 三处都拿得到**（原 OQ3/OQ5）：`RosterPlayer` 带 `player_id`（api.ts:142）；排阵/对手对比用的
  `LineupPlayer` 只带 `key`，但后端 `key=f"{KEY_PREFIX}{player.id}"`（`lineups/query.py:341`），player_id
  可从 key 还原。propose 定：给 `LineupPlayer` 加一个 `player_id` 字段（additive）比在前端剥前缀更干净。
- **批量读端点形态**（原 OQ4）：定为 by-ids——`GET /api/players/notes?ids=1,2,3` 返回
  `{player_id: PlayerNote[]}`。三处都能用、与「哪支队」解耦；空/缺失的 id 返回空。走 backend secret（读）。
