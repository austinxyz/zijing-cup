## Context

`players` 上的五个字段（当前单/双打 UTR、各自状态、`utr_profile_id`）一个都没有值。
写入通道其实早就通了 —— `PATCH /api/players/{id}` 接受全部五个，中间件也已按 HTTP
方法保护住 —— 缺的只是**入口**：迁移不带这些数据，名单 CSV 没有这些列，界面上没有
任何编辑口。

因此本 change 的重心不在后端，而在「一张表怎么安全地在人和库之间往返」。

真正的技术难点只有一个：**这一行是谁**。上一个 change 的名单迁移是按姓名归并的，
代价可见（2026 ZJU-USC 那 18 人是猜的）。但这里猜错的后果不可见：

```
姓名/profile 匹配错
  → A 的当前 UTR 落到 B 身上（一个完全合理的数字）
  → B 本赛季没有参赛 UTR 时，推导链第二步拿它当 B 的实力
  → 排出一套「看起来合法」的阵容，而它不是
```

名单导错顶多多一个人少一个人，一眼能看出来；UTR 导错没有任何外显症状。

## Goals / Non-Goals

**Goals:**

- 一条能安全批量填这五个字段的通道，且**不含任何身份猜测**。
- 写库之前把全部后果摆在人面前，包括他没打算改的东西。
- 名单页上补一个人不必走一趟往返。
- 让推导链第二步从死路变成活路。

**Non-Goals:**

- 吃 UTR 官网的导出文件（`utr-export-ingest`，已在 backlog）。
- 与 UTR 官网同步 / 抓取。
- 动 `player_season_utrs`（参赛 UTR 有自己的裁决与锁流程）。
- 导入历史 / 审计表。
- 改推导链本身。
- 移动端版式。
- 任何 schema 变更。

## Decisions

### D1. 往返，而不是匹配

表由**我们**导出，已带 `players.id`；人只填 UTR 那几列；导回时按 id 落位。id 从我们
这儿出去、原样回来，中间没有「这一行是谁」这个判断。

**替代方案**：吃 UTR 官网导出 + 一屏匹配确认界面。否决 —— 那是本 change 两倍多的工作量，
且在拿到一份真实导出文件之前是凭空设计（上一次「拿抓来的表格当事实源」的教训）。
更要紧的是：项目负责人明确指出 **profile ID 会变、姓名会重**，两者都不能当依据，而
自增 id 两者都不受影响。

### D2. 姓名是校验位，不是备选匹配依据

姓名随 id 一起往返，导入时核对 `id` 指向的人是否还叫这个名字。对不上就整批停下。

这防的是**唯一一种往返会坏的方式**：行被打乱、或粘贴时错了行。此时 id 与姓名会成对
错开，校验立刻抓到。

**关键的反面**：`id` 缺失或不认识时 MUST NOT 回退到姓名匹配 —— 那等于把 D1 的保证
在最需要它的那一刻撤掉。spec 里为此单独配了一条 scenario。

### D3. 「空」的三种含义各自明确

| 单元格 | 含义 | 理由 |
|---|---|---|
| 空白 | 不改 | 最常见用法是只填几个人；当成清空会在第一次导入时抹掉一整队 |
| `-` | 清空回 null | 不给这条路，一个填错的值就再也回不到「没有」 |
| 只有值没状态 | 整行错误 | 没有状态的数字推导链用不上，页面上却照常显示 |

第三条是「错的标签比没有标签更糟」在这里的具体形态：一个孤零零的 6.72 会显示在名单页
的当前双打列里，看的人以为它能用，而推导链根本不会采纳它。

### D4. 两步：先差异，后写入；有错误则整批不写

解析产生一个**纯数据的差异结果**，人确认后才落库。

整批拒绝而不是「写好的那部分」，是因为最常见的严重错误是**整列粘错位**，那时几乎每行
都会出错。放行一半会让库里一半新一半旧，而没有任何记录说明哪一半是新的 —— 这个状态
比全部失败难恢复得多。

### D5. 差异屏按人分组，并用「按字段的改动计数」补回列扫描

版式由项目负责人在视觉稿上选定（B 版）。代价是列不对齐，看不出「一竖排都在变」这个
整列粘错的信号。补法是顶部一行按字段的改动计数：只填了三个人的双打却看到「单打 12 处」，
就是粘错了列。计数明显偏高的格子标 warning 底。

**替代方案**：逐字段表格（A 版），列天然对齐。已由负责人否决，理由是窄。

### D6. 解析与比对是纯函数，放 `backend/app/players/utr_sheet.py`

与既有四个导入器（规则 / 名单 / 队名 / 队员迁移）同一形态：解析 → 读库 → 比对 →
只写差异。差异计算不碰 session，因此可以对着手造的行测试，不需要数据库。

TSV（粘贴）与 CSV（上传）在**解析入口**归一成同一种行结构，之后共用一条路径 ——
两个入口给出不同结果会让人无从判断该信哪个。

### D7. 路由 `teams/[code]/utr`，自带登录门与 error.tsx

由负责人在视觉稿上选定：离名单最近，正在看这支队时右上角一个按钮就进来了。

代价是 `players/layout.tsx` 的登录门覆盖不到这里，要照着再配一份。`error.tsx` 同样
不能省 —— 这是项目里记过的教训：路由自己没有错误边界时，一次冷启动超时会从「某一块
加载失败」变成「整个应用崩了」。

### D8. 批量写是一个事务，且只认这五个字段

一条失败整批回滚，与 D4 的「整批不写」在两层各实现一次（界面拦一次，端点再拦一次）。

端点 MUST NOT 借此改姓名或性别：一个能顺带改姓名的「UTR 导入」会让 D2 的校验位
失去意义 —— 校验完再把姓名改掉，下次就对不上了。

## Risks / Trade-offs

- **[人在 Sheets 里把 id 列删了或重排了]** → 姓名校验位会抓到重排；整列删掉则每行都
  报「id 缺失」，属于响亮失败。代价是必须重新导出一份，这是有意的。
- **[负责人嫌往返多一步，回头想直接吃官网文件]** → 已记为 backlog 的
  `utr-export-ingest`；本 change 的解析层按行结构设计，那个 change 可以复用比对与
  差异计算，只需换掉「行 → id」这一段。
- **[`utr_profile_id` 的真实链接形态未知]** → spec 写成「链接与纯 ID 都接受，取不出
  ID 则报错」。取不出时报错而非存原文，避免库里混进半结构化的字符串。拿到真实链接后
  可以收紧。
- **[当前 UTR 改动会影响另一组的页面]** → 属实且正确（一个人只有一个当前 UTR），
  但反直觉，所以差异屏必须点名跨组的队员。
- **[就地编辑与批量导入两条路做同一件事]** → 边界划在「一个人」与「一队人」：就地编辑
  一次只能改一名队员，不提供同屏多改。

## Migration Plan

无 schema 变更，无 migration。五个字段都已存在且可空。

**回滚**：本 change 新增的是端点与页面，`git revert` 即可。已经通过它写进去的当前 UTR
会留在库里 —— 这是数据而不是结构，回滚不应删除它；届时那两列会退回「只显示、没法改」
的状态。

**部署顺序**：后端先上（新端点对旧前端不可见），前端后上。反序会让页面调到不存在的
端点。
