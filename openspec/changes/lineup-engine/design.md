## Context

`competition-rules` 提供了规则（各线 cap、buffer 额度、分值、资格阈值），
`team-roster` 提供了名单与参赛 UTR，两者都已上线。本次是第一个同时消费两者的能力。

探索阶段做了两件量化工作，结论直接决定了实现方式，记在
`docs/superpowers/specs/2026-08-28-lineup-engine-requirements.md` 的「探索阶段测得的事实」：
穷举可行（分支限界跑完 24 支真实球队最坏 1.61 秒），以及目标函数会顶满预算后大面积并列。

视觉稿：`design/Lineup.dc.html`、`LineupLocked.dc.html`、`LineupBlocked.dc.html`
（画布第四页）与 `docs/superpowers/specs/mocks/2026-08-28-lineup-engine-mocks.html`。

## Goals / Non-Goals

**Goals:**

- 一个纯函数的求解核心：名单 + 规则 + 锁定 + 排除 → 候选、上限、状态。
- 一条只读端点，锁定与排除走 query。
- 一个排阵页：锁定控件、排除名单、结果区，三种非正常状态各自可见。

**Non-Goals:**

- 对手对比、胜负预测、外援校验、金组第一级抢先、持久化、移动端版式。
- 「是哪一条锁定导致无解」的归因。

## Decisions

### 分支限界，不用启发式，也不用策略模式

路线图原本写的是「移植 MatchApp 的策略模式阵容优化引擎」，前提是搜索空间太大。
实测这个前提不成立：完整阵容组合数虽然是 24 万到 288 亿，但

- 女双的合法搭档极少（3~35 对，女队员本就少），
- 每条线的 cap 把候选搭档砍到几十到二百多对，
- 目标是最大化总和，一旦拿到接近上界的现任解就能大面积剪枝。

按合法搭档数从少到多定线序（WD → MD → D3 → D2 → D1），以「剩余各线最强搭档之和」
为上界剪枝，24 支真实球队全部在 1.7 秒内跑完，多数低于 0.05 秒。

**精确穷举比启发式更值得要**：上限报告要求「没有任何合法阵容能超过这个数」，
启发式给不出这个保证。

### 目标函数：上场十人参赛 UTR 之和最大

有 cap 的线会顶死在 cap 上，多出来的实力只能进开放线，所以这个目标在金银两组都
成立（实测金组 `THU-UOC` 的最优解正是这个形状）。

**它与金组 4:4 平局的第二级抢先方向相反**——那一级是「上场十人总 UTR 低者胜」。
这是已知代价，结果呈现不得暗示「顶满 cap 在任何情况下都占优」。

### 上限 + 十人去重，而不是「Top 5」

目标会顶满预算后并列：实测两支队在 56.00 各有 400 套以上并列、其中 175/177 组是
不同的十人；另有五支队 270 套以上并列却只对应**同一组十人**。后者按「Top 5」呈现，
等于把一套阵容重排五遍冒充五个选项。

所以：候选按**上场十人的集合**去重，并单独报告「可达上限」与「达到它的十人组合数」。
这两个数把「上限」和「推荐」分开——顶点可能没得选，选择发生在次优那一层。

### 求解核心是纯函数，不碰数据库

输入是已经读出来的名单记录与规则值，输出是数据结构。理由与 `app/rosters/parse.py`
相同：约束逻辑要能用虚构数据密集测试，不该每次都要一个数据库。读库与组装响应
留在路由层。

### GET，锁定与排除进 query

`team-roster` 有一条断言「OpenAPI 里不存在任何写方法」并有测试守着，本次不放宽。
锁定最多五对、排除最多几名，query 装得下。附带两个好处：阵容链接可以直接发给队友；
与前端既有的「URL 是唯一事实来源」一致。

### 节点预算与截断

Render 免费实例的 CPU 比开发机慢数倍。搜索带节点预算，触到就停，并在结果里标明
**不完整**。把截断的结果当作完整搜索呈现，等于让人以为「就这些了」。

预算值在实现时定；开发机上最坏用了 346 万节点，预算应当明显高于它，否则常见情况
也会被截断。

### 无解诊断只到「哪条线」

无解时报告哪条线的候选搭档集合为空，并可以列出相关队员当前的去向（被锁进哪条线、
被排除）——那是读输入，不需要重新搜索。

**不做**「是哪一条锁定该负责」：要逐条去掉锁定重算，最多五次完整搜索，在 Render 上
代价不成比例，且多条锁定共同导致时仍然指不准。界面上要把这个区别写明，否则
「谁去了哪」会被读成因果归属。

### 侧栏拆成「阵容」与「对手对比」

原来的「分析」一项含义含糊，而对手对比是本次明确不做的功能。两者同名会让人以为
已经能比对手了。

## Risks / Trade-offs

- **[Render 上的实际耗时未知]** → 开发机最坏 1.61 秒，Render 免费实例慢数倍，可能到
  5~10 秒，叠加冷启动近一分钟。缓解：节点预算 + 截断如实报告 + 页面有等待态。
  真实耗时要在部署后测一次，不能靠开发机的数字承诺。

- **[Decimal 全程]** → 参赛 UTR 是精确小数，10.25 与 10.2 对 cap 是不同答案。
  搜索里有大量加减比较，任何一处退化成 float 都会在边界上给出错误判定，而且
  很难被发现。测试要覆盖「恰好等于 cap」与「恰好等于 buffer 额度」。

- **[资格限制是数据不是常量]** → 高 UTR 阈值、人数上限、允许线位都来自
  `division_eligibility_limits`，其中 `restricted_to_lines` 可空。实现要把「不限线位」
  与「限定某几条线」都走通，不能只处理有值的情况。

- **[并列的稳定性]** → 并列极多，排序在相等时的次序取决于搜索顺序。同样的输入
  应当给出同样的输出，否则刷新一次候选就换一批，读起来像坏了。次序要可复现。

- **[锁定的搭档本身非法]** → 队长可能锁一对超 cap 或差距超限的搭档。这要被识别为
  「你锁的这对不合法」，而不是「搜不到」——后者会让人以为是名单的问题。

## Migration Plan

无 migration，无 schema 变更，无写端点。

1. 本地：跑测试；用 2025 真实名单对 24 支球队各搜一次，确认全部返回或如实报告截断。
2. `git push` → Render 部署后端、Vercel 部署前端。
3. 部署后在远程测一次最坏情况（`SJTU-XJTU`，开发机 346 万节点）的实际耗时，
   据此复核节点预算是否合适。

回滚：前端回滚即可；后端新增的是只读端点，留着不影响任何现有行为。
