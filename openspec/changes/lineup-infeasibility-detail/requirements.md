# lineup-infeasibility-detail

排阵在某条线**凑不出任何合法搭档**时，现在只说「`{线}`没有任何合法搭档」——不说
**为什么**。用户排阵时撞到的就是这个：知道 WD 没解，但不知道是人不够、都超 cap、还是
被自己的排除/锁定吃掉了人。本次给这个「为什么」补上，并**归因到用户自己的锁定与排除**
（当那是直接原因时）。

这是三条阵容增强里最自包含的一条（A）。保存过滤（B）、保存阵容 + 失效标记（C）各自
单列，不在本次。

## 背景（探索阶段读到的事实）

- 后端 `app/lineups/search.py`：某条线的 `legal_pairs()` 返回空时，`search()` 提前返回
  `infeasible_line=<线code>` + `placements`（谁被锁进哪条线 / 谁被排除）。**只有线 code，
  没有原因。**
- `legal_pairs()` 逐对过四关：性别组合（`_slot_ok`）、搭档差距（`partner_gap_max`）、
  cap + buffer 余量、资格线限制。全过则留下，全被刷掉就空——**原因在过滤时丢了**。
- 前端 `LineupStates.tsx` 的 `NoSolution`：说「{线}没有任何合法搭档」+ 列 `placements`，
  并**明确声明不做因果归因**（注释：逐条拆锁重算太贵，且多锁叠加会算错）。
- **锁本身非法**（`invalid_locks`，超 cap 多少 / 超差距 / 又锁又排…）已有很细的中文
  message，本次**不重做**。

## Goals

- 某条线 `infeasible_line` 时，后端**给出为什么**：结构化的原因，覆盖常见几类——
  - **性别组合人手不足**：这条线需要的组合凑不齐（如 WD 需 2 名女队员，可用不足 2）。
  - **都超 cap**：能凑出组合，但每一对的参赛 UTR 之和都超过 cap + buffer 余量。
  - **都超搭档差距**：能凑出，但每一对差距都 > `partner_gap_max`。
  - **资格线限制挡了**：候选里够格的人被「高 UTR 只能打某几条线」的限制排除在本线外。
- **归因到用户自己的锁定/排除 —— 仅当那是直接、可读出的事实**：这条线的合格人手是被
  哪些排除 / 锁进别线的人抽走的，就点名他们（「WD 需 2 名女队员；周乐言被排除、韩雨萌
  锁进 MD，只剩 1 名」）。这不是猜「哪条锁导致全局无解」，是数「这条线还剩几个够格的人、
  少的那几个去哪了」。
- 前端 `NoSolution` 把原因与归因讲清楚，取代现在光秃秃的「没有任何合法搭档」。

## Non-Goals

- **不做深层（assignment 级）无解归因**：每条线单看都有搭档、但整套凑不出（两条线抢同
  一个人）——不在本次。本次只处理「某条线自己的候选池为空」。
- **不改锁本身非法的诊断**（`invalid_locks` 已够细）。
- **不做因果猜测**：MUST NOT 声称「是这条锁定/这次排除**导致了**无解」。只陈述可直接
  读出的事实（这条线的合格人手数、少掉的人现在在哪）。现有注释警告的正是这种猜测，
  本次守住它。
- **不做保存过滤（B）/ 保存阵容（C）/ per-user 登录 / 任何存储**。
- 不改搜索算法、cap/buffer/资格规则本身、候选呈现（对比表/紧凑行）。

## Constraints

### 架构

- 后端 `zijing_cup` schema 无新表、无 migration —— 只在响应里多一个诊断结构。
- 诊断是**只读**计算：`infeasible_line` 那条线的候选池分析，MUST NOT 触发第二次整解
  搜索（性能 + 「不逐条拆锁重算」的既定纪律）。
- 前端经 `lib/api.ts` 单一出口取数；诊断字段加进 `LineupSearch` 类型。

### 诊断的真实性（守住既有不变式）

- 原因按**客观可判**给出：性别组合人数、cap、差距、资格，是这条线候选池为空的直接算
  得出的事实。多个原因可并存（有人卡 cap、有人卡差距），据实列出，MUST NOT 只挑一个
  猜「主因」。
- 归因**只在直接事实成立时**给：某类合格人手因排除 / 锁进别线而减少，就点名那些人及其
  去向（复用 `placements`）。MUST NOT 把「松开某条锁就一定有解」当承诺——只说「这些人
  现在不可用」这个事实。
- 数值一律用后端给的字符串，前端 MUST NOT 拿显示值做比较。
- **资格线限制是规则属性，不是用户造成的**：它作为「为什么这条线没人」的一个客观原因
  据实呈现（「某人 UTR 高于 X，只能打某几条线」），但 MUST NOT 归因到用户的锁定/排除。
  归因（点名 + 去向）只针对**被排除 / 被锁进别线**这两种用户动作；资格、cap、差距是
  规则或队员自身属性，据实说原因、不点名成「你干的」。

### 呈现

- `NoSolution` 面板沿用既有样式档（warning/中性），显式给 `bg-surface`；对比度 ≥ 4.5:1
  实测 computed style。窄视口（<768）与桌面都要读得清、不横向溢出（沿用 mobile-shell/
  lineup 的地基）。

### 测试

- 后端 pytest：为每类原因造一个最小无解场景，断言诊断结构里有对应原因与（可归因时）
  点名的人。`npm run test` 不校验类型，`npx tsc --noEmit` 单列。
- 本地看页面前不跑 pytest（会清库）；顺序：先测试 → 补种 → 视觉核对。

## Success Criteria

1. WD/MD 这类需要特定性别组合的线，可用该性别人数不足时，诊断给出「需要 N 名 X 队员、
   可用只 M 名」，前端显示。
2. 能凑出组合但每对都超 cap + buffer 时，诊断给出「都超 cap」类原因；都超差距时给出
   「都超搭档差距」；资格限制挡住时给出资格原因。多因并存时都列出。
3. 当这条线缺的合格人手正是被排除 / 锁进别线的人，诊断**点名**他们及去向；无可归因时
   只给客观原因，不硬凑归因。
4. 诊断**不触发第二次搜索**（只读候选池分析）；响应里不出现「哪条锁该负责」这类因果
   断言。
5. 前端 `NoSolution` 用原因 + 归因取代「没有任何合法搭档」一句；桌面与 375 都读得清、
   0 对比度不合格、无横向溢出。
6. 锁本身非法（`invalid_locks`）路径与改动前一致。
7. `npx tsc --noEmit` 干净；vitest 与 pytest 全绿。

## User Stories

- 作为队长，WD 排不出来时我想知道是「我女将本来就不够」还是「我把某个女将排除了 / 锁进
  了混双」，好决定松开哪一个，而不是对着「没有合法搭档」发呆。
- 作为队长，如果是全队女将本来就只有 2 个、还有 1 个 UTR 太高被 cap 卡住，我想它直接告诉
  我「都超 cap」，省得我一个个试。
- 作为队长，我不想它对我撒谎——如果它说不清到底哪条锁该负责，就别装作知道。

## Open Questions

1. 诊断结构长什么样：`infeasible_line` 旁加一个 `infeasibility: { reasons: [...], blocked_relevant: [...] }`？
   还是把原因塞进现有 `Violation` 列表复用前端渲染？—— design 定。
2. 「性别组合人手不足」里，"可用" 的口径：roster 减去被排除、减去锁进别线的人。混双
   （MD）需一男一女，女不足与男不足要分别报。—— design 敲定计数口径。
3. 资格限制原因的措辞与归因边界（资格是规则属性、不是用户锁的，不归因到用户）。—— design。
4. 前端 NoSolution 的视觉：原因列表 + 归因点名的排布（窄视口如何堆叠）。—— Phase 4 视觉稿。

## Referenced Capabilities

- `lineup-ui` —— 本次改的能力（`NoSolution` 呈现）。
- `lineup-search` —— 后端诊断在这条能力里（`app/lineups/search.py` 出更细的 infeasible
  原因）。两条能力都会有 delta。

## 探索阶段测得的事实（补充细节）

- `legal_pairs(rules, rule, pool)`：`combinations(pool,2)` 过 `_slot_ok`（性别组合）→
  `partner_gap_max` → `cap + min(buffer_per_line, buffer_total)`。空则该线无解。
- `pool` = roster 去掉被排除的；`available` 再去掉锁进任何线的人。诊断要基于同一口径。
- `placements`（`_placements(locks, blocked)`）：key → 线code 或 "excluded"。归因就读它。
- `NoSolution` 现有免责声明（不逐条拆锁重算、不声称哪条锁该负责）—— 本次归因只做局部
  事实，不违反它；requirements 的 Non-Goal 把这条界线写死了。
