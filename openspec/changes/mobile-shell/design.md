## Context

四条读路由今天都是桌面三栏，壳是 `h-screen min-h-[640px] overflow-hidden`。手机上
横向溢出，而 `overflow-hidden` 让溢出**不出现滚动条** —— 内容被静默裁掉。

关键约束来自 Next.js 的渲染模型：**服务端渲染时没有视口宽度这个信息**。layout 与
page 在服务器上跑，那里只有 URL 和请求头。这一条决定了下面几乎所有的结构决策。

既有代码里已经定型、本次要沿用而不是重造的东西：

- 导航选中态由 `useSelectedLayoutSegment()` 从 URL 推导（`ActiveSidebar`），球队列的
  选中态同理（`SelectedTeamList`）。手机 tab 条走同一条路子。
- 赛季切换器是原生 `<details>`，零客户端 JS。
- 排阵页的控件已经是一个 **plain GET form + 显式提交**（`LineupControls.tsx:75`），
  改约束本来就不会自动触发搜索。手机面板沿用它，不引入行为分叉。
- 壳在 layout 而非页面内部，`error.tsx` 替换的是它下面的内容。

## Goals / Non-Goals

**Goals:**

- < 768px 时四条读路由可用：不横向滚动、不静默裁切、可点区域够大。
- 手机与桌面**共用一套路由与一份数据获取**，不出现两份并行实现。
- 顺带补上 `utr_profile_id` 的链接（三处）与两个 token 的对比度。

**Non-Goals:**

- 管理界面（队员管理、UTR 批量往返表）的手机版式。
- 冷启动加载态（单独 change）。
- 桌面布局的任何改动 —— 行高、列数、列宽不变。
- 后端与数据库改动。

## Decisions

### D1 断点取 768px，用 Tailwind 默认的 `md:`，不加自定义断点

多一个断点就多一处将来会与设计稿分歧的数字。768 把手机与小平板竖屏划到手机版式，
iPad 横屏留在桌面三栏 —— 三栏在 1024 宽是舒服的，在 800 宽已经挤。

**替代方案**：1024 作为断点（平板也走手机版式）。否决理由是 iPad 上会变成一屏只看得到
一个东西，而三栏在那个宽度还能用。

### D2 手机与桌面同一套路由，由 CSS 决定哪一列可见

**这不是取舍，是被逼的**：服务端看不见视口，按设备拆路由只能靠 user-agent 嗅探 ——
UA 不可靠，而且会把同一个 URL 的缓存按设备切开。

具体做法：`teams/layout.tsx` 照旧同时渲染球队列与 `children`，两侧各挂
`hidden md:flex` / `md:hidden` 之类的类，由当前 segment 决定哪一侧在手机上可见
（segment 已经在 `SelectedTeamList` 里读了，不必新增机制）。

**代价，说清楚**：手机在名单屏也下载了球队列的 HTML（18 行，几 KB）。
**不叠加延迟** —— `teams/layout.tsx` 取球队列、`teams/[code]/page.tsx` 取名单，
Next 并发渲染两者，冷启动时它们是一次等待而不是两次。

**用 `display:none` 而不是 `visibility`/`opacity`**：隐藏的一侧必须从无障碍树里消失，
否则屏幕阅读器会读到两份导航、两份球队列表。

### D3 壳的高度模型重定：`100dvh`，去掉 `min-h-[640px]`，滚动放在顶栏之下

三处一起改，缺一不可：

- `h-screen`（`100vh`）在移动端按地址栏收起后的高度算，页面比可视区高一截 → 改
  `100dvh`。
- `min-h-[640px]`：667 的屏减去顶栏 95px 就只剩 572，这条最小高度会直接造成溢出 →
  窄视口下不施加。
- 滚动容器必须在**顶栏与 tab 条之下**那一层。放在它们的共同祖先上，顶栏会跟着卷走；
  给顶栏加 `flex-none` 并不能钉住它（滚动在共同祖先上时它照样走）。

`overflow-hidden` 本身留着 —— 它是「壳不滚动，内层滚动」这个模型的一部分。危险的是
「`overflow-hidden` 且内层没有滚动容器」，不是 `overflow-hidden` 本身。

### D4 导航是一份数据、两个呈现组件，不是一个组件塞两套 DOM

抽一份 nav 项定义（label / icon / href / 是否未开放 / 在哪些 section 高亮），
`Sidebar` 与新的 `TopNav` 各自消费。

**替代方案**：一个组件内部按断点渲染两套 DOM。否决理由是那个组件会同时承载深色侧栏的
纵向布局与顶栏的横向布局，两套间距、两套选中态样式挤在一个文件里，改一处很容易碰坏
另一处。

tab 条比侧栏**少一项**（无「队员管理」），这个差异写在数据的消费侧而不是数据源里 ——
数据源列出全部导航项，`TopNav` 过滤掉管理项。这样「手机上没有队员管理入口」是一处
显式过滤，不是一个恰好没被列进去的遗漏。

### D5 名单在手机上换一套 DOM，不是把表格 CSS 变形

桌面名单是 `<table>`（7 列），手机是逐行的列表（序号 / 姓名+性别 / 参赛 UTR + 来源）。
两者字段集**不同**（手机不要当前单/双打），行结构也不同（手机是两层）。

用 CSS 把 `<table>` 改成块级并重排，得靠 `display:block` 打散表格语义，还得用伪元素
补标签 —— 那条路做出来的东西对屏幕阅读器是坏的，而且做不到「隐藏两列并把来源换行」。
所以是两套 DOM，各自 `hidden` / `md:hidden`。

**代价**：名单的行渲染逻辑有两份，改字段要改两处。缓解：把「一名队员的展示数据」
（参赛 UTR、来源标签文案、是否可链接）抽成一个纯函数，两套 DOM 共用它 —— 会分歧的是
排版，不是判定。

### D6 排阵约束面板的开合是纯本地 UI 状态，不进 URL

约束本身（锁定、排除）已经完全由 URL 表达，这条不动。**面板开着还是关着**不是结果的
一部分，把它塞进 URL 会让「同一份结果」有两个不同的链接。

面板内仍是那个 plain GET form，提交即导航 —— 与桌面同一个行为，同一段代码。

### D7 UTR 网址是一个常量加一个纯函数，放 `frontend/lib/`

`profileUrl(id: string): string`，唯一一处 `https://app.utrsports.net/profiles/`
字面量。三处消费方（名单页、队员详情、队员列表）都引用它。

`id` 为空时**不调用它**，由调用方决定不渲染链接 —— 让函数返回一个空串或 `#`，就会
出现点不动的链接，那正是要避免的形态。

### D8 只改两个 token 的值，不新增 token、不新增暗色系

| token | 改成 | 依据 |
|---|---|---|
| `--color-muted` #79736a → **#6b665d** | 在 `--color-surface-muted` #f2efe9 上 4.09 → **4.97** | 所有表头用的是这一对 |
| `--color-sidebar-fg-dim` #6f6a60 → **#8f8a7e**，并去掉 `PendingNavItem` 的 `opacity-45` | 合成后 #413f38 on #1c1b18 = 1.63 → **5.01** | 禁用态改用颜色表达，不用透明度 |

`--color-muted` 变深波及桌面 ~76 处，全部只是颜色变深一点，不改布局。

**禁用态不再用 `opacity`** 是这条的要点：不透明度会把前景色与背景色混在一起，
**源码里读不出最终对比度**。用一个明确的颜色 token 表达禁用，量的时候量到的就是
真实值。

## Risks / Trade-offs

- **[两套 DOM 会分歧]** 名单与导航各有手机/桌面两套结构，改字段容易只改一边 →
  把判定逻辑（来源标签文案、是否可链接、排序）抽成共用纯函数，两套 DOM 只负责排版；
  为「同一名队员在两种视口下的判定一致」配测试。
- **[`--color-muted` 波及 ~76 处]** 改一个 token 影响面远大于本次改动的表面 →
  视觉核对不能只看手机屏：桌面的表头、徽章、说明文字都要过一眼；验收断言落在
  computed style 的实测数字上，不靠肉眼。
- **[隐藏的一侧仍在 DOM 里]** 手机上球队列虽不可见但存在，若用错了隐藏方式会造成
  重复的导航/列表被读屏软件念两遍 → 统一用 `display:none` 类；配一条断言隐藏侧不在
  无障碍树里。
- **[窄视口下没有队员管理入口]** 管理员在手机上无法到达管理界面 → 已接受的取舍，
  写进 spec 与 README；不做成一个点了横向滚动的入口。
- **[窄视口下看不到当前单/双打 UTR]** → 用 UTR 官网链接补上，且链接给的是权威值而不是
  人工维护的副本；但 `utr_profile_id` 填充率未知，可能大部分人没有链接。空态必须
  看起来正常。
- **[`100dvh` 的浏览器支持]** 老 iOS Safari 不认 `dvh` → 用 `100dvh` 时保留
  `100vh` 作为前一条声明（CSS 自然回退），最坏情况退回今天的行为而不是布局崩掉。

## Migration Plan

纯前端改动，无数据库变更、无 API 变更、无环境变量变更。Vercel 部署即生效，回滚即
回滚上一个部署。

桌面用户会看到的唯一变化是两个 token 的颜色与三处新增链接 —— 不需要任何用户侧动作。
