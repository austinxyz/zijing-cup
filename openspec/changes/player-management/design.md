## Context

需求见 `docs/superpowers/specs/2026-08-29-player-management-requirements.md`，
视觉稿见 `docs/superpowers/specs/mocks/2026-08-29-player-management-mocks.html`。

现状的三个事实决定了本次的形状：

1. **库里没有任何身份证据。** 探索阶段读了本地 459 行真实数据：375 个不同姓名，83 个
   姓名出现在多行（其中 82 个是同一人在金银两组各一行，规则允许），而带
   `utr_profile_id` 的行数是 **0**。字段早就存在但从未被填过。
2. **17 个人的两行参赛 UTR 不同**，全是清华的（金组 `THU-UOC` 对银组 `THU-I`/`THU-II`）：
   Zong Qingqing 6.25/6.38、Liu Rayne 7.82/7.84……两张总表分别冻结、取样差几天。
3. **本项目至今没有写接口**，且有测试守着「OpenAPI 里不存在写方法」。鉴权模型是单一
   共享密钥，它证明「请求来自我们的服务器」，不证明「这是谁」。

`roster_entries` 当初刻意不建 `players` 表（migration 注释里的 D1），理由正是第 1 条。
本次不推翻那条判断，而是接受它的前提并补上缺的那一半：猜一个身份，但让人能改。

## Goals / Non-Goals

**Goals:**

- 队员成为跨赛季实体，可独立于队伍维护。
- 参赛 UTR 按 `(人, 赛季)` 存，带状态、Appeal 标记与**来源**。
- 成员关系按 `(人, 队伍)` 存，带代表学校、外援、外卡。
- 合并与拆分：冲突不阻塞合并；拆分逐行决定归属。
- 管理员写入口：默认拒绝、凭据不进浏览器。
- 迁移两季全部行，且不自行裁决冲突。

**Non-Goals:**

- 读路径切换（下一个 change）。本次落地后，管理界面的修改在名单页与排阵页上看不见。
- 导入器改写（再下一个）。窗口期暂停导入。
- 多角色权限、UTR 同步、操作历史、移动端版式。

## Decisions

### D1：三张表，不复用 `roster_entries`

`players` / `player_season_utrs` / `player_team_memberships` 三张新表，全部建在
`zijing_cup` schema。`roster_entries` 原样保留，本次不动它一行。

**为什么不在 `roster_entries` 上加列**：那张表的语义是「某赛季某组别某队的一行名单」，
而队员是跨这三者的。硬加 `player_id` 会让一张表同时是快照又是关系表，且迁移期间它既是
读来源又是被改的对象——出问题时无法回滚到「迁移前」。三张新表让本次的所有写入都发生在
一个全新的、没有任何东西读它的地方，这是本次能安全上线的主要原因。

**替代方案**：给 `roster_entries` 加 `player_id` 外键并逐步回填。放弃，理由同上。

### D2：身份键是「规范化姓名」，UTR 链接是将来的证据

迁移按 `trim` + 转小写后的 `姓+名` 归并。**不做模糊匹配**：`Xie Yuntao "Young"` 这类
带引号别名、以及 `Guanpeng | Chen` 这种两栏填反的行，任何自动规则都会在一部分行上猜对、
另一部分猜错，而猜错的那部分没有痕迹。规范化规则写死并有测试，验收标准才可判定。

UTR 链接是**将来**让合并可验证的键，但今天一条都没有，所以它不能作为迁移的依据。
界面把「没有链接」显示出来，是为了让这件事被慢慢补上。

### D3：冲突用「两个候选值 + 未裁决标记」表示，读取时取大

`player_season_utrs` 一条记录带 `value`、`alt_value`（可空）、`is_unresolved`。未裁决时
`value` 存较大者、`alt_value` 存较小者，读取一律返回 `value`。

**为什么不存成两行**：两行会让「(人, 赛季) 唯一」这条约束失效，而那条约束正是本次模型的
核心；一旦允许两行，下游每个读的地方都要重新决定挑哪行，等于把冲突扩散出去。

**为什么取大**：参赛 UTR 在规则里几乎全部用作**上界**判定。取小会把一套其实违规的阵容
显示成合法，到赛场才暴露；取大只会少给几个本来合法的选项，是看得见的。方向不对称，
所以没有「中立」的默认值可选。

裁决可以填两个候选之外的第三个值——真值可能是组委会后来的更正。

### D4：鉴权是中间件的第二层，形状与现有那层一致

`app/auth.py` 现有中间件是减法式的：新路由不声明就已受共享密钥保护。管理员校验加成
**同一个中间件里的第二个判断**——按 HTTP 方法判定：`POST/PUT/PATCH/DELETE` 一律要求
`X-Admin-Secret`，与路由前缀无关。

**为什么按方法而不是按路由前缀**：前缀是约定，靠人记得把写路由放进去；方法是请求本身
的属性，漏不掉。将来若出现「写方法但不需要管理员」的路由，那是显式豁免，与 `/health`
今天的处理方式一致。

**为什么不用 FastAPI 依赖**：依赖是加法式的——忘了挂就没有保护，而这正是现有中间件注释
里写明要避免的失败模式。

`ADMIN_SECRET` 缺失时拒绝全部写请求。与现有那两段检查一样，**两个条件分开写**，不折成
`if expected and provided != expected`——后者在变量未设置时会放行一切。

### D5：登录在 Next 侧，会话是签名的 httpOnly cookie

浏览器只与 Next 通信这条架构纪律不变。登录页收口令，服务端比对**哈希**（环境变量存
哈希，不存明文），通过后签发 httpOnly cookie；写操作走 Server Action，服务端校验 cookie
后才带上 `BACKEND_SECRET` + `ADMIN_SECRET` 调 FastAPI。

失败限速用**内存计数**（按 IP + 固定窗口）。Render 免费实例是单进程，够用；不引 Redis。
限速状态必须回传给界面——剩余次数只在后端存在而前端不说，用户会以为是自己手滑。

**替代方案**：JWT。放弃——只有一个管理员、只有一个服务端消费者，JWT 的可验证性没有用武
之地，却带来密钥轮换与过期语义的复杂度。

### D6：纯逻辑与数据库访问分开

归并规则、冲突判定、拆分的行归属都是纯函数（输入是已读出的行，输出是决定），放
`app/players/` 下与 `query`/`command` 分开。理由同 `app/lineups/`：这些规则要用虚构数据
密集测试，不该每次都要一个数据库。

写入本身（事务边界、唯一约束冲突的处理）留在 command 层。

### D7：迁移是一条可重复执行的命令，不是 migration 里的 DML

Schema 变更走 `supabase/migrations/`；数据搬运走 `python -m app.players.migrate`，
形状与现有的 `load_rules` / `load_rosters` 一致：解析 → 读现状 → 比对 → 只写差异，
`--check` 复用同一个比对函数并转成退出码。

**为什么不写进 migration**：远程是手工在 Dashboard 执行 SQL 的（CLAUDE.md 那条 no-CLI-push
规则），一条几百行的 DML 在那里执行既不可观测也不可重试。命令可以先 `--check` 看它打算
做什么，再执行。

## Risks / Trade-offs

- **[管理界面的修改在前台看不见]** → 这是 Out of Scope 的直接后果，窗口从本次落地持续到
  读路径切换。缓解：C 紧接本次做；本次界面上要说明「这里的修改会在下一步生效」，
  不能让人以为前台坏了。
- **[写接口是新的攻击面]** → 缓解：按方法判定的减法式中间件（漏不掉）、密钥缺失时全拒、
  凭据不进浏览器、登录限速。风险仍在于共享密钥本身泄漏——那时读接口会丢，但写接口还挡着
  第二层，这正是选方案 B 而不是 A 的理由。
- **[按姓名归并会把两个同名的人并成一个]** → 缓解：合并可拆分。但拆分不可撤销且没有操作
  历史，拆错了只能手工搬回去。这是本次明确接受的代价（Non-Goals 不做审计日志），界面必须
  在执行前把后果摆出来。
- **[未裁决取大会少给合法选项]** → 明确接受。反方向（取小）会给出赛场上被判无效的阵容，
  两者不对称。
- **[迁移把 2026 的手工修改覆盖掉]** → 2026 银组 ZJU-USC 的 Qingyang Zhang 是人直接写进
  `roster_entries` 的。迁移读的就是那张表，所以她会被正常迁进来；但**迁移必须在窗口期
  开始前跑完**，否则期间的手工改动会分叉。缓解：迁移 `--check` 先跑一次并核对人数。
- **[内存限速在多实例下失效]** → Render 免费实例是单进程，当前成立。若将来扩容，这条要
  重做；注释里写明这个前提。

## Migration Plan

1. 本地：建 schema（把 migration 的 SQL 直接打到本地栈，执行前断言连接串含 `127.0.0.1`
   ——本机跑不了 `supabase` CLI，见 CLAUDE.md）。
2. 本地：`python -m app.players.migrate --check` 对 2025 数据跑一次，核对：队员数 = 规范化
   姓名去重后的人数、未裁决数 = 17。
3. 远程：在 Supabase Dashboard 手工执行 migration 的 SQL（不用 CLI push——共享项目的
   migration 追踪表是全项目共用的）。
4. 远程：把 `DATABASE_URL` 指向远程跑一次 `--check`，确认两季全部行都被认领，再执行。
   **跑完立刻 `unset DATABASE_URL`**——同窗口接着跑 pytest 会清空线上数据。
5. Render 与 Vercel 各加环境变量（`ADMIN_SECRET`、管理员口令哈希），再部署。
6. 回滚：三张新表没有任何东西读它们（读路径在下一个 change 才切），删表即可回到迁移前。
   `roster_entries` 全程未被修改，这是回滚成立的前提。

## Open Questions

- **删除的确切语义**：Constraints 已定「仅在没打过或赛前允许」，判定依据是赛季锁。
  剩下的问题是——真删除行，还是保留并标记？倾向真删除：没有历史记录的人删掉不留痕，
  与「有历史就删不掉」合起来足够安全，且不引入第二种「存在但不算数」的状态。
- **合并候选怎么找**：本次先做手工发起（选两个人 → 合并）。系统主动扫同名并推荐留到
  以后——82 个同名里绝大多数是同一人的正常情况，主动推荐会产生一个几乎全是噪音的队列。
- **未裁决标记要不要给非管理员看**：本次只在管理界面呈现。排阵页上的呈现属于读路径切换
  那个 change，届时再定。
