# 能力清单

`openspec/specs/` 下每个目录是一个已归档的能力（capability）。这里维护一份清单，方便快速找到"这功能是哪个 change 做的、覆盖了什么"。

### `competition-rules` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为队长，我想按赛季和组别查到本组的完整赛制规则（各线 cap、buffer、分值、资格限制），排阵前不必翻公众号长文去找那几个数字；也想看到去年的规则，这样今年 cap 变了（银组混双 10.5→10.25）我能立刻知道去年那套阵容是否还合法。作为开发者，我想让这些值以数据形式存在，明年改规则改的是一个 seed 文件，而不是散落在排阵算法里的常量。

**覆盖需求**:
- docs/superpowers/specs/2026-08-27-rules-and-design-system-requirements.md（赛制规则数据模型、seed 与导入、只读查询、赛制规则页面）
- 领域依据见 docs/domain/rules.md

**后台**: `zijing_cup` schema 下四张表 —— `seasons` / `divisions` / `division_lines` / `division_eligibility_limits`。不用 JSONB，因为两件事要能被 schema 表达并查询：`division_lines.cap` 为 NULL 即金组的开放线（是另一种线，不是上限很高的线，且分值不同），`division_eligibility_limits.restricted_to_lines` 是可空 text[]，让「UTR>9.0 男队员 ≤1 名且只能打 D1/MD」这条同时带人数上限与线位白名单的规则装进一行；NULL 表示不限线位，check 约束拒绝空数组（那读作「一条线都不能打」）。`buffer_per_line` 与 `buffer_total` 分两列 —— 2026 两组恰好相等，但规则原文是两条独立约束，一列会断言它们永远相等。`mens_doubles_must_be_ordered` 只存开关；判定方式已定（三条男双线的参赛 UTR 之和非递增，相等不算违规——见 docs/domain/rules.md §6），判定本身属 `lineup-engine`。

规则内容以 `backend/seeds/rules/{year}-{division}.toml` 为唯一事实来源，标准库 `tomllib` 读取（零新依赖，且能在每个数值旁贴规则原文出处）；数值写成字符串按 Decimal 精确解析 —— TOML 浮点存不下 0.30，而这些数字决定阵容合法与否。导入命令 `python -m app.seeds.load_rules` 走「解析 → 读库 → 比对 → 只写差异」，`--check` 复用同一个比对函数并转成退出码，供 CI 拦截「改了 seed 忘了导入」的漂移。seed 中消失的规则集按删除处理（否则 seed 就成了只增不减的叠加，不再是事实来源）。同赛季两个组别的 `[season]` 块不一致会在解析阶段拒绝 —— 它们共用一行 `seasons`，不一致会导致导入永不收敛。

HTTP 侧只读：`GET /api/seasons`（赛季×组别索引，驱动切换器）与 `GET /api/seasons/{year}/divisions/{code}/rules`（单组别完整规则，三次查询组装，无 N+1，不加缓存）。**没有任何写入端点** —— 规则一年改一次，走 seed 文件 + code review + 导入命令，测试断言 OpenAPI 里不存在指向规则资源的写方法。开放线序列化为 JSON null，未知赛季或组别返回 404 而非空对象。

**前台**: `app/[season]/[division]/rules/` —— Server Component 经 `lib/api.ts` 单一出口取数。开放线显示「开放线」而非数字；Buffer 卡片明说「共享预算，不是每线容差」（五线各超 0.2 合计 1.0 是非法的，这是最容易误读的一条）；记分组别多显示各线分值。「较上一赛季」在页面内比对（额外取一次上赛季规则），上一赛季不存在时正常渲染且不显示对比 —— 最早的赛季本就没有上一届，不是错误。后端不可达时走 `rules/error.tsx`，壳仍在。

**验收标准**: 四套规则（2025/2026 × 金/银）可查；金组 2026 的 D1/MD `cap IS NULL` 且分值为 1/2/2/1/2 合计 8；银组 2026 五线 cap 为 13/12/11/10.25/9.25 且 buffer 0.50；银组 2025 的 MD/WD 为 10.5/9.5 且无 buffer；导入命令幂等且 `--check` 能检出漂移；规则页对未知组别 404。

### `app-shell` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为队长，我想在任意页面都能一眼看到当前是哪个赛季哪个组别，并一步切到另一组；作为开发者，我想让后续页面直接复用已定型的侧栏与基础组件，而不必在每个 change 里重新决定布局与配色。

**覆盖需求**: docs/superpowers/specs/2026-08-27-rules-and-design-system-requirements.md（设计系统移植、应用壳、URL 路由约定）

**后台**: 无。本能力纯前端，数据来自 `competition-rules` 的两个只读端点。

**前台**: `frontend/app/globals.css` 的 token 块与 `components/ui/{button,card,badge,input}.tsx` —— 全部逐值移植自 ai-course-management（两个应用要看起来是一家人，重新推导出的"差不多"配色就是这件事悄悄失效的方式），零新增运行时依赖，`cn` 是手写四行。相对源项目两处有意偏离：不移植 `.dark`（本应用没有任何地方切换它，移过来就是会静默漂移的死代码）；Badge 去掉 `info`、加 `warning`，用于「合法但有代价」这一档（超 cap 但由全队 buffer 覆盖的搭档，读作 danger 是错的）。

`app/[season]/[division]/layout.tsx` 承载 216px 深色侧栏。壳在 layout 而非页面内部：`error.tsx`/`loading.tsx` 替换的是其下方内容，壳若在页面里，一次取数失败会清空整个窗口（ai-course-management 踩过）。赛季×组别切换器是原生 `<details>`：收起是一个控件标签，展开列出**全部**组合，当前项标记且不可点。选项是链接不是客户端状态 —— URL 决定哪套规则生效，React 里再存一份就会与地址栏分歧。尚未实现的「队伍」「分析」呈现为禁用态并标注「未开放」，不做成点了没反应的死键。

2026-08-28 起「队伍」是真链接（指向该赛季组别的球队列表），当前区段由 `useSelectedLayoutSegment()` 从 URL 推导——此前「赛制规则」的选中态是写死的，队伍页可达后会在队伍页上谎称当前在规则页。

2026-08-29 起「分析」这一项被拆掉：含义含糊，而对手对比恰恰是当时明确不做的功能，同名会让人以为已经能比对手了。现在是**「阵容」**（真链接，指向排阵页；在球队页与排阵页上会带上当前这支队，免得再选一次已经在看的队）与**「对手对比」**（保留禁用态与「未开放」标注）。同一批改动里修掉一处对比度事故：赛季切换器的药丸底色用的是 `bg-background`——那是浅色内容区的页面底色，配上近白的标签只有 1.05:1，等于看不见。侧栏是有自己配色的页面外壳，因此新加 `--color-sidebar-well`（#14130f，视觉稿本来的值）而不是从内容区借一个 token，改后 16.07:1。

2026-08-30 起再多一项**「队员管理」**（真链接，指向管理界面）。未登录时点它会跳到登录页，
而不是打开一个空的管理界面——已实现的入口就该是链接，只是它后面需要一个会话。侧栏同时
第一次有了登录态：已登录显示身份与登出，未登录什么都不显示（让读页面的人看见一个身份，
会误读成谁都能改东西）。「阵容」取当前作用域里的球队时只认 `teams` 与 `lineup` 两个区段——
`/players/42` 的第二段是队员 id，当成球队 code 会拼出一个 404 的链接。

**验收标准**: 切换器列出所有 (赛季, 组别) 组合且集合不随选择变化；「队伍」是链接且在队伍页高亮，「分析」不是链接；后端不可达时侧栏仍渲染、仅内容区变错误态；客户端 bundle 中不含 `BACKEND_URL` / `BACKEND_SECRET`。

**mobile-shell（2026-08-31）**: < 768px 时侧栏变形为顶栏 + 一条 tab 导航（队伍 / 阵容 / 对手对比 / 赛制规则；队员管理**不上** tab 条，管理界面不做手机版式，代价是手机上无入口到达它）。一份 nav 数据源喂两个呈现组件（`Sidebar` / `TopNav`），tab 少一项是消费侧显式过滤而非漏列。壳的高度模型重定：`100dvh`（保留 `100vh` 回退）、窄视口不施加 `min-h-[640px]`、滚动容器放在顶栏之下那层——三者缺一，内容会被 `overflow-hidden` 静默裁掉且不出滚动条。顺带修三个既有对比度缺陷（见下），并把 token×底色对比度写成承重测试 `globals.contrast.test.ts`。

### `team-roster` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为队长，我想把组委会总表里的名单一次导进来、之后按赛季和组别查，而不是每次排阵都去 Google Sheet 里翻；作为组织者，我想在导入时就知道哪些行没读懂、哪些队人数不对，而不是等排阵算出怪结果才发现名单缺了人。

**覆盖需求**: docs/superpowers/specs/2026-08-28-roster-import-requirements.md（名单数据模型、CSV 导入与字段归属、对账报告、只读查询）

**后台**: `zijing_cup` schema 下两张表 —— `teams` / `roster_entries`。~~没有 `players` 表~~ —— 这条在 `player-registry` 落地后不再成立，且本能力的**查询端已于 `read-path-switch` 改读注册表**：跨年身份先按姓名给一个猜测，再由管理员合并或拆分，「这两行是不是同一个人」从此有答案。`roster_entries` 仍在，但只作为回滚依据与迁移命令的输入源，唯一键仍是 `(赛季, 组别, 球队, 姓, 名)`。`is_borrowed_player` 是三态可空布尔且**无默认值** —— NULL 读作「没人标过」，与 false（「确认不是外援」）是不同的断言，而外援有每队与每场的人数上限，这个区别决定一套阵容到底有没有被真正检查过。

解析与导入分离：`app/rosters/parse.py` 是纯函数（文本进，记录与报告出），`load.py` 走「解析 → 读库 → 比对 → 只写差异」，`--check` 复用同一个比对函数。导入只覆盖 CSV 拥有的五个字段（`gender` / `match_utr` / `dutr_status` / `source_note` / `daily_utrs`）—— 外援标记与 UTR 档案链接由人手工维护，整行重写会把它们清掉。

总表是工作文档而非导出格式，解析器有一半工作是**说出它读不懂的东西**：表头不在第 1 行（前有空行与两行脚注，按内容在前 20 行内定位）；合并单元格脚注漏成了数据行（`Borrowed Player` / `Unrated/Projected/Appeal` 两个伪队名跳过并报告）；取样列日期逐年变（按前缀匹配）；取样格里可能写着 `Early Lock` 这类文字注记（跳过该次取样、**保留球员**，按球员合并后报告 —— `Match UTR` 才是权威值，为一个佐证列丢掉一名真实球员是错的取舍）。`NaN` 反而整行拒绝：它能被 `Decimal` 解析，进库后与任何 cap 比较都返回 false，一条含 NaN 的阵容会看起来通过了所有限制。

评级类别只在能判定时判定：`Rated`→已认证、`Projected`→委员会审定，`Unrated` 留 NULL —— 它属于第 2 类还是第 3 类取决于该队员有无 USTA 比赛历史，总表不带这个信息，猜一个就等于替人决定了谁占用「场上至多 2 名自评级」的名额。

球队另有一个**人工维护的中文显示名**（`display_name`，可空、无默认值），以 `backend/seeds/team_names/*.toml` 为唯一事实来源，由 `python -m app.seeds.team_names` 导入，形态与规则 seed 相同（解析 → 读库 → 比对 → 只写差异 + `--check`）。它是第四个「导入器不碰」的字段。两条纪律写进了测试：从 seed 中消失的条目按**清空**处理（否则 seed 成了只增不减的叠加），而作用域取自**文件**而非条目——早期版本按条目取作用域，导致「只导银组」会把金组的名字全清空并报告成正常的移除行。seed 指向不存在的球队时报告未匹配但不失败：先导名单再导显示名是正常顺序，拼错 code 才是要被看见的。

HTTP 侧只读：`GET /api/seasons/{year}/divisions/{code}/teams`（含 `player_count`、`display_name` 与男/女/性别未填三档人数，一次分组查询，无 N+1——有一条测试直接数 SELECT 条数，把「不许退化成每队一查」锁住）与 `.../teams/{team_code}/roster`。第三档不是冗余：`gender` 可空，并进任一侧会让那侧凭空多一个人。**没有任何写入端点** —— 本项目不做 per-user 登录，一个公开的写接口等于谁都能覆盖所有队的名单，测试断言 OpenAPI 里不存在写方法。

**前台**: 本次无。两条端点已上线待 `roster-display` 消费。

**read-path-switch（2026-08-31）**: 两个只读端点换源到队员注册表，人数改数成员关系条数、性别取自队员记录。响应形状不变，`dutr_status` / `source_note` / `daily_utrs` 保留但**恒为 null**（新来源不存它们，配了一条 scenario 把这件事钉成有意为之）；`match_utr` 与新增的 `origin` 一起放宽为可空 —— 新模型允许「在队但一个数都取不到」，而这种人**仍要出现在名单里**，否则球队列的人数与名单条数会对不上且页面不说。这一条是评审拦下来的：实现当时把他 `continue` 掉了，注释还写着「丢掉会误报阵容」。另新增当前单/双打 UTR 及其状态四个字段（推导链第二步的输入）。CSV 导入器加了自锁：默认拒绝执行并说明这些行不会被任何页面读取，`--i-know-it-is-not-read` 可绕过且仍打印同一句 —— 只输出「+N 行」而网站毫无变化，是一次成功的假象。

**验收标准**: 2025 赛季金组 6 队 120 人、银组 18 队 339 人落库；两个伪队名不出现在球队表；重复导入报告无变化且不产生重复行；导入器一次都不写 `is_borrowed_player`；`Unrated` 行的 `rating_class` 为 NULL 而非猜测值；名单 CSV 不进版本库（`custom_verification_checks` 按内容扫描前 20 行拦截）。

### `team-roster-ui` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为队长，我想在浏览器里翻名单——左边看到本组所有球队和各队人数，点开一支就看到完整名单和每个人的参赛 UTR，按强弱排好；我还想一眼看出哪几支队女队员卡在下限，以及哪些队员的评级类别还没定。

**覆盖需求**: docs/superpowers/specs/2026-08-28-roster-display-requirements.md（路由与选中项、球队列信息取舍、名单表与 UTR 来源呈现、空状态与错误态）

**后台**: 无新增数据模型。数据来自 `team-roster` 的两个只读端点，本次为它们扩了球队显示名与三档性别人数（见该能力条目）。

**前台**: `app/[season]/[division]/teams/` —— 球队列在 `layout.tsx`（两条路由共用，且 `teams/[code]/error.tsx` 失败时只替换名单区，球队列仍在，而换一支队正是失败后的出路），空状态在 `page.tsx`，名单在 `[code]/page.tsx`。选中的球队由 `useSelectedLayoutSegment()` 从 URL 段推导，不存客户端状态——存一份就会与地址栏分歧，刷新与分享链接都会丢。空状态**不重定向到第一支球队**：那会让地址栏自己变，而「第一支」只是字母序的偶然。

球队列显示 code + 总人数 + 男/女人数。这是全篇最实质的一处取舍：场上要 1 名女子打混双、2 名打女双，至少 3 名女队员是硬约束，而 26 人名单的平均 UTR 跟真正上场的 8 个人关系不大。女队员数 <4 时该数字加重——合法但零余量，所以用字重而不是状态色（状态色留给「待定」，同一屏两种「注意但不是错误」用同一颜色会分不清指什么）。性别为空单列第三档，并入任一侧会让那侧凭空多一个人。

名单表按后端给出的次序渲染，前端**不再排一次**——参赛 UTR 打平很常见（多人压在同一个 cap），两处各排一次会给出两个答案。「UTR 来源」原本同时给出判定类别与总表原文；`read-path-switch` 之后**原文不再存在于数据来源里**，因此只剩类别：`verified`→已认证、`committee`→委员会审定、`captain`→队长评定、为空→**「待定」**，绝不显示「自评」。Appeal 从原文里的后缀变成独立标志，以 `<类别> · Appeal` 呈现 —— 不专门处理就会随原文一起静默丢掉。

滚动放在内层容器：球队列本身 `overflow-hidden`、列表滚动，名单区同理、表头 `sticky`。放在外层会把列头与队名一起卷走。壳是 `h-screen overflow-hidden`，不自带滚动容器的长列表会被直接裁掉且不出现滚动条——这个缺陷是交付后由项目负责人在真实窗口里发现的，五轮评审与视觉对照都没抓到（对照是在「刚好放得下」的视口下做的）。

**验收标准**: 2025 银组 18 队 339 人、金组 6 队 120 人；某队三档性别人数之和等于总人数；`Unrated` 行显示「待定」且整页不出现「自评」；未知球队 code 返回 404 且「没有这支球队」呈现在内容区内、侧栏与球队列仍在；26 人名单与 18 行球队列在 760px 高的窗口里可滚到底；客户端 bundle 不含 `BACKEND_SECRET`。

**mobile-shell（2026-08-31）**: 窄视口下球队列表与名单是**两屏**（同一套路由 + CSS 决定可见性，不按 user-agent 嗅探——服务端看不见视口），名单从表格换成逐行卡片、**丢掉当前单/双打两列**（要看实时值点姓名去 UTR 官网），名单页姓名在有 `utr_profile_id` 时可点开 `app.utrsports.net/profiles/<id>`（桌面也加）。名单页带「‹ 球队列表」返回条（`md:hidden`）。管理员的行内编辑在手机上是一个 `role=dialog` 编辑抽屉（Escape、聚焦首字段、44px 目标），赛季未锁时说明「保存会把参赛 UTR 一并改成同一个值」。

### `lineup-search` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为队长，我想给出几对已经定下的搭档和本场上不了的人，让系统在剩下的空间里把五条线补齐，并告诉我这套限制下最强能排到多少、有多少种十人组合能达到它；如果根本凑不出合法阵容，我要知道是哪条线卡住了，而不是收到一个空列表让我猜是没搜到还是没有解。

**覆盖需求**: docs/superpowers/specs/2026-08-28-lineup-engine-requirements.md（约束集与目标函数、锁定与排除、去重与上限语义、无解与截断的报告契约、只读端点）

**后台**: `backend/app/lineups/` —— `rules.py`（合法性判定，纯函数）、`search.py`（分支限界搜索）、`query.py`（唯一读库的地方：读规则与名单、调纯函数、组装响应）。只读端点 `GET /api/seasons/{year}/divisions/{code}/teams/{code}/lineups`，锁定与排除走可重复的 query 参数（`lock=LINE:keyA,keyB`、`exclude=key`）。**没有新增任何写方法**——阵容不落库，每次按名单与规则重算，因此也没有东西需要写；「OpenAPI 里不存在写方法」那条断言继续成立（断言读 `app.openapi()["paths"]`，不遍历 `app.routes`——后者在当前 FastAPI 版本里看不见任何 `/api` 路由，会静默通过）。

合法性是五条约束的合取：逐线 cap 加每线 buffer、各线超出量之**和**不超过全队 buffer 额度、搭档差距、三条男双非递增（相等不算违规）、高 UTR 的人数与线位。**逐线独立判定 buffer 会放出五线各超 0.2、合计 1.0 的非法阵容**，所以预算必须整队一起算。开放线（金组 D1/MD）表达为 `cap = null` 而不是一个很大的数字，既不参与 cap 校验也不消耗 buffer。全程 `Decimal`：10.25 与 10.2 对 cap 是不同答案，任何一处退化成 float 只在边界上错，而边界正是最难发现的地方。所有阈值来自 `competition-rules` 的数据，没有一个是代码常量。

搜索精确穷举而非启发式——报告的上限必须真的是上限，启发式给不出这个保证。线序按合法搭档数从少到多（女双最少），以「剩余各线最强搭档之和」剪枝。候选按**上场十人的集合**去重：同一批十人换线不算两套，否则「前 N 名」会把一套阵容重排 N 遍冒充 N 个选项。并列极多（实测某队 400+ 套），所以次序必须可复现，同样输入给同样输出。

三种非正常状态各有独立字段，都不用空列表表达：`infeasible_line`（哪条线没有合法搭档）、`truncated`（触到节点预算，结果不完整）、`borrowed_players_checked`（恒为 false）。第四种是 `invalid_locks`：锁定会跳过逐线筛选，不单独报会变成「你的名单排不出来」，而真相是「你要的这条锁定本身违规」。`placements` 只报「谁现在在哪」（读输入即得），**不声称知道是哪条锁定导致无解**——那要逐条拆锁重算，多条共同导致时仍指不准。

**前台**: 无。本能力是引擎与端点，界面见 `lineup-ui`。

**read-path-switch（2026-08-31）**: 名单读取换源到队员注册表，并新增**参赛 UTR 推导链**（`app/players/utr_chain.py`，纯函数）：本赛季冻结值 → 当前 `rated` 双打值 → **最近一个有值赛季**的 match UTR（不限上一年）→ 都取不到则不参与排阵。这是组委会自己的算法，不是排阵的内部技巧，因此名单页与引擎**共用同一条链**，对同一名队员必须给出同一个数字（配了一条跨模块断言）。结果新增三个计数：未参与计算、含估算值、未裁决（未裁决取较大值——参赛 UTR 是上限，取小会把违规阵容说成合法）。逐名队员另带 `origin` / `origin_year` / `is_unresolved`。

**BREAKING**：队员 key 从 `roster_entries.id` 改为带前缀的 `p<player_id>`，使旧分享链接里的裸数字**解析失败**并明确报「链接是旧格式」。两套 id 都是小整数且互不相干，不换格式的话旧链接会静默锁到两个不相干的人，而算出的阵容看起来完全正常。同期把 `origin` 的兜底默认值去掉，改成缺失即 KeyError —— 给一个查不到来源的数字盖「组委会冻结」的章，比崩掉更糟。

**验收标准**: 2025 全部 24 支真实球队（金 6 + 银 18）各搜一次，全部返回完整结果、0 截断，开发机最坏 0.09s（2025 两组 buffer 均为 0.00，可行空间小；2026 开了 buffer 会变慢，Render 免费实例的真实耗时仍需部署后实测）；小名单上穷举全部合法阵容，最大值等于报告的上限；锁定被遵守、排除被遵守、换线不算两套；未知球队 404，格式非法的 query 返回 4xx 而非 500；OpenAPI 中仍不存在 POST/PUT/PATCH/DELETE。

### `lineup-ui` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为队长，我想在页面上锁定几对搭档、勾掉本场不能上的人，然后看到按强弱排好的候选阵容，每条线的两个人、性别、该线之和与超出量都摆在那里；我还想把这套搜索的链接直接发给队友，他打开看到的是同一套限制。

**覆盖需求**: docs/superpowers/specs/2026-08-28-lineup-engine-requirements.md（锁定与排除的 URL 表达、结果区信息次序、三种非正常状态的呈现）；视觉稿 `design/Lineup.dc.html`、`LineupLocked.dc.html`、`LineupBlocked.dc.html`

**后台**: 无新增。数据来自 `lineup-search` 的只读端点，经 `frontend/lib/api.ts` 单一出口取数。

**前台**: `app/[season]/[division]/lineup/[code]/`（页面、锁定面板、结果区、状态面板、错误边界）与 `lineup/page.tsx`（没指定球队时的选队页——侧栏的「阵容」总得落到一个真页面上）。路由**不放在 `teams/[code]/` 下面**：那会继承球队列布局，多出一列与视觉稿不符。

锁定与排除是一个原生 GET 表单，**不进 React state**：存一份就会与地址栏分歧，刷新与分享都会丢，而分享链接正是这页的用法。一条线只有两个位置都填了才算锁定——半填的表单不是约束。

结果区先给可达上限、规则允许的上限、两者差值、达到上限的十人组合数，之后才是候选：顶部常是几百套并列，「能到多高、顶点有没有得选」与「该挑哪一套」是两个问题。有锁定时**并发**跑第二次无约束搜索算出锁定的代价——不并发的话两次整解在冷启动的免费实例上叠加会超时。候选必显示性别：高 UTR 限制分性别设定，不显示就无法照界面核对这条约束。

三种非正常状态各有面板，无解那块指名线位、列出相关队员去向，并附「这是读当前输入的结果，不是哪条锁定该负责」；外援免责无条件出现在任何结果上（沉默会被读成「查过了」）。两条路由各有 `error.tsx`：取数失败只换内容区，侧栏与锁定面板还在——没有它就会冒泡到根 `error.tsx` 把整个窗口清空。

**read-path-switch（2026-08-31）**: 顶部两条新提示 —— `本结果含 N 名参赛 UTR 未裁决的队员，按较大值计算`（warning）与 `本队 N 人因缺少参赛 UTR 未参与计算`（中性），N 为 0 时都不出现。估算值标**三处**：队员的数字旁 `估算`、整套候选上 `含 N 个估算值，合法性待总表确认`、可达上限旁 `含估算值` —— 合法性是整套的属性，线内之和、全队 buffer、高 UTR 人数都会用到那个数字，一个估算值就让「这套合法」本身成为估算；上限那处则是全页最容易被单独转述的数字。旧格式链接以中性档（**不是 danger**，它是提示不是危险操作）呈现 `这个链接是旧格式（队员编号已变），请重新选择锁定的搭档`，并给一个不改 URL 就能继续的入口；页面**不发出带旧 key 的搜索**，否则会得到一份忽略了锁定、看起来完好的候选列表。真实数据实测顶部最多同时三条提示约 135px / 640px，未构成提示墙，按需求文档的约定就地定案不再收拢。

锁定面板 520px 宽（视觉稿是 420）：排除标签一人一个，26 人的名单在 420 宽下要占十行，把面板顶过 640px 高的窗口，于是面板自己出滚动条而页面不滚。宽度是从候选卡那边匀过来的，且过了约 460 金组的卡就会折到第三行——460 到 520 之间躲不掉这个代价，所以取 520（余量最大）。长列表仍各自带滚动容器（壳是 `h-screen overflow-hidden`，不带滚动容器会被静默裁掉且不出现滚动条）。

**验收标准**: 锁定与排除写在 URL 里且直接访问该 URL 得到同一套限制；结果区四个数（可达上限/规则允许/差值/组合数）在候选之前；候选显示五线搭档、性别、各线之和、超出量与 buffer 用量；锁定使上限下降时页面呈现该差值；无解时不渲染空候选列表且指名线位；截断与外援未校验各自可见；26 人名单在 660px 高的窗口里锁定面板不出滚动条、候选列表可滚到底且表头不动；客户端 bundle 不含 `BACKEND_SECRET`。

**mobile-shell（2026-08-31）**: 窄视口下排阵页**结果打底**，锁定/排除控件收进底部抽屉（`role=dialog`）；关闭态一条摘要**点名到人**（「已锁 陈嘉禾·吴普强 · 排除 …」，不只给数量——受约束结果与无约束最优在屏上长得一样）。改约束不自动搜索（沿用既有 GET form 的显式提交，一次搜索在冷启动免费实例上是整解）。抽屉自带滚动、44px 目标；桌面仍是左栏控件。

**lineup-results-redesign（2026-09-01）**: 候选阵容从 20 张叠卡改成**桌面对比表**（真 `<table>`+`table-fixed`：行=候选、列=名次/总和/buffer + 五线；列对齐可竖扫「谁在 D1」，同分不同搭配一眼分辨；名字不换行截断带 `title`，表头滚动钉住，表体自带滚动）与**手机紧凑行**（名次+总和+D1 签名+代价角标，点开展开五线纵向 + buffer）。既有合法性信号不丢，但密集视图里逐字「估算」改成紧凑角标（数字 `˟`、整套「估」badge / 含估算 flag），完整句「含 N 个估算值，合法性待总表确认」挪到图例/悬停/手机展开态保留一处——标记不省略、整句不删只挪（spec MODIFIED 放宽了这一条）。判定 helper 抽 `candidate.ts` 两套 DOM 共用，`CandidateCard` 退役；不重排候选（`keep=20`）。纯前端，不动后端。另：锁定搭档的下拉选人改成先按性别（男→女→未填）、组内按 UTR 从高到低（`orderForSelect`，数值比非字符串比；排除 checkbox 仍按后端序）。

### `admin-access` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为项目负责人，我想让只有我能改队员数据，而任何人都能照常读规则、名单与阵容；我也想让将来新加的写接口默认就是受保护的，不依赖谁记得挂上什么。

**覆盖需求**: docs/superpowers/specs/2026-08-29-player-management-requirements.md（写接口防护、登录会话、凭据不进浏览器、限速）

**后台**: `app/auth.py` 现有中间件加第二层，按 **HTTP 方法**判定：`POST/PUT/PATCH/DELETE` 一律要求 `X-Admin-Secret`。按方法而不按路由前缀，是因为前缀靠人记得把新路由放进去，方法是请求自带的属性；同理不用 FastAPI 依赖 —— 依赖是加法式的，忘挂就是敞开。`ADMIN_SECRET` 未配置时拒绝全部写请求，两个条件分开写（折成一个 `if expected and provided != expected` 会在变量未设置时放行一切）。

**前台**: `app/login/` 的登录页与 Server Action，`lib/session.ts`（scrypt 口令哈希、HMAC 签名的 httpOnly cookie、两小时有效期、登录限速）、`lib/admin.ts`（唯一的写入口：先校验会话，再带两个密钥调 FastAPI；任一密钥缺失即抛错，不发空 header）。不用 JWT —— 只有一个管理员和一个服务端消费者，可验证性没有用武之地。

限速有两个桶：按地址 5 次，另有一个 header 影响不到的**全局** 20 次。只按地址计数是不够的 —— 地址来自请求头，轮换一下就绕过了；全局那道才是让轮换失去意义的东西。剩余次数回传给界面，否则用户会以为是自己手滑，一路试到被锁。

**验收标准**: 无凭据的写请求返回 401/403；`ADMIN_SECRET` 未配置时全部写请求被拒；新增一条不声明任何鉴权的写路由同样受保护（拆掉中间件的写检查后守卫立刻变红，验证过不是空转）；读路由不受影响；客户端 bundle 不含任何凭据；会话 cookie 是 httpOnly 且两小时过期。

### `player-admin-ui` ✅ 已实现 · 🌐 已上线
**用户故事**: 作为管理员，我想在一个页面里看完一个人是谁、今年多少、在哪几支队；想在发现两条记录是同一个人时合并、发现一条其实是两个人时拆开；也想知道哪些参赛 UTR 还没裁决，因为在裁决之前排阵结果只是保守估计。

**覆盖需求**: docs/superpowers/specs/2026-08-29-player-management-requirements.md；视觉稿 `docs/superpowers/specs/mocks/2026-08-29-player-management-mocks.html`（核心五屏）

**后台**: 无新增数据模型。取数经 `lib/api.ts` 单一出口，写入经 `lib/admin.ts`。列表的总数与「未裁决」条数来自服务端（`X-Total-Count` 与 `?unresolved=true`），**不从当前这页的行里数** —— 页面上限 200，数出来会是 7 而真值是 17，且屏幕上没有任何东西说这个数字是局部的。

**前台**: `app/[season]/[division]/players/`。`players/layout.tsx` 一处校验会话（每页各写一次的失败模式，是后来加的那页忘了写）。这套界面的约束大多是同一件事：**不让不确定的数字看起来确定**。未裁决与预填同一档警示色（是同一个事实：组委会还没确认）；未裁决的地方写明「现在按较大值算」而不只说「有冲突」；裁决允许填第三个值（真值可能两个候选都不是）；批量确认存在但不长得像默认动作 —— 它把保守估计变成已确认的事实。

合并与拆分不可撤销，两者都在执行前把结果摆出来：拆分两侧各自列出最终拥有哪些记录（错误永远是「这行跟错人了」，只有两边都摆出来才看得见），合并则说清谁留谁删、以及哪个赛季会因此变成未裁决。警告用 danger 档，与「未裁决」的 warning 档分开 —— 一个说「看一下」，另一个说「这收不回来」。

**验收标准**: 一人多队时列表列出全部队伍；未裁决与预填同档标记；缺 UTR 链接可见但不是错误态；徽标与截断提示的数字来自服务端；详情页三块同屏且未裁决横幅写明当前采用值；队列每行显示两个候选值**及其来源总表**（按记录的来源归列，不按大小）与当前采用值；未登录访问管理界面跳转登录页。真实数据实测：队列 17 行，一次裁决后 16 行、来源变 `admin_ruling`。

**mobile-shell（2026-08-31）**: 队员列表与详情页的 UTR 链接从不可点文字/「有」改成真链接（指向 `app.utrsports.net/profiles/<id>`，`rel=noopener noreferrer`，缺失仍显示「无」且不是链接）。**不做手机版式**——管理界面在窄视口下仍是桌面版式需横向滚动，是既定取舍。

### `current-utr-io` ✅ 已实现 · ⏳ 待上线
**用户故事**: 作为队长，我想把一支队的名单导成一张已经写好 id 和姓名的表，拿去 Google Sheets 里照着 UTR 官网填，填完整块贴回来，而不是在页面上一个个点开改 26 次；我想在真正写库之前看见「这次会改谁的什么」；临时补一个人时我想直接在名单页上改，不必为一个人走一趟往返。

**覆盖需求**: docs/superpowers/specs/2026-08-31-current-utr-source-requirements.md；视觉稿 `docs/superpowers/specs/mocks/2026-08-31-current-utr-source-mocks.html`（四屏）

**后台**: 无新增数据模型 —— 五个字段（当前单/双打 UTR、各自状态、`utr_profile_id`）在 `players` 上早就存在，缺的一直是入口。`app/players/utr_sheet.py` 是纯函数层（解析 → 比对 → 差异），TSV 与 CSV 在**解析入口**归一成同一种行结构；`app/routers/utr.py` 提供按队取导出行、preview、apply 与按 id 批量写。

这块能力的全部设计围绕一件事：**绝不猜「这一行是谁」**。id 从系统出去、原样回来，姓名同行带回只作校验位；`id` 缺失或不认识时 **MUST NOT** 回退到姓名，spec 为此单独配了一条 scenario。理由是猜错的后果不可见 —— 名单导错一眼看得出，UTR 导错是一个合理范围内的数字落在错的人身上，页面上完全正常，却会喂给推导链排出「看起来合法」的阵容。负责人另指出 profile ID 会变、姓名会重，两者都不能当依据。

「空」有三种含义各自明确：空白 = 不改（最常见用法是只填几个人，当成清空会在第一次导入时抹掉一整队）、`-` = 清空（不给这条路，填错的值就再也回不到「没有」）、值与状态必须成对（孤零零的数字推导链用不上，页面上却照常显示）。数值按 `Decimal` 比较而不是按字符串 —— `7` 与 `7.00` 是同一个 UTR，按文本比会把满屏没人做过的改动摆出来。

**赛季未锁时，写当前双打 UTR 同时把该赛季的参赛 UTR 设成同一个值**，覆盖不论原来源。取样窗口之前参赛 UTR 根本不存在，手填的当前值是唯一能排阵的数。**锁是这条覆盖唯一的护栏** —— 组委会数据一导入就立刻锁季，所以「已有组委会数据」与「赛季未锁」在流程上不重叠；忘了锁则一次手填会无声覆盖冻结值（已知代价，见 design D9）。当前 UTR 本身照旧不受锁限制。

**前台**: `app/[season]/[division]/teams/[code]/utr/`（导出/导入两页签 + 差异屏 + 自己的登录门与 `error.tsx` —— 它在 `teams/` 下，`players/layout.tsx` 的门覆盖不到）与名单页的行内编辑。差异屏按人分组，代价是列不对齐、看不出「一竖排都在变」这个整列粘错信号，因此顶部补一行**按字段的改动计数**把那个信号换种形式给回来。有任何一行被拒 → 确认按钮禁用、整批不写。跨组的队员被点名 —— 当前 UTR 是人的属性，改完另一组页面看到的也是这个值。

**验收标准**: 原样导出、原样导回产生 0 处改动；行被打乱或粘错位时姓名校验位整批拦下；`id` 为空而姓名唯一匹配时仍然报错；状态写 `Rated` 接受、写 `已认证` 整行拒绝；真实数据实测一次完整往返（贴表 → 差异 → 确认 → 名单页可见 → 排阵页标「估算」）；赛季未锁时参赛 UTR 跟着变、锁上后不动；差异屏全部文案对比度 ≥ 4.5:1（实测 computed style，改前 28 个元素不合格）。
