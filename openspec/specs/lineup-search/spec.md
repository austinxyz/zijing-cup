# lineup-search Specification

## Purpose
把「这套阵容合法吗」和「这支队最强能排到多少」变成可计算的问题，取代队长拿计算器
逐对试 cap。合法性是五条约束的合取——逐线 cap、全队共享的 buffer 预算、搭档差距、
三条男双非递增、高 UTR 的人数与线位——漏掉任何一条都可能到赛场才被判无效，而
cap 只是其中一条。

求解是纯函数：名单与规则值进，候选、可达上限、违规项出，不碰数据库。分支限界精确
穷举而不用启发式，因为报告的上限必须真的是上限——启发式给不出这个保证。

三种非正常状态是一等公民，都不得用空列表表达：**无解**（并指出哪条线凑不出）、
**搜索被截断**、**外援限制未校验**。空列表读作「搜过了没找到」，与「这套限制本身
没有解」是不同的断言。对外只有一个只读端点，锁定与排除走 query——阵容不落库，
没有任何东西需要写。
## Requirements
### Requirement: 阵容合法性由一组约束共同判定
系统 SHALL 把一套阵容的合法性判定为下列约束的合取，缺一不可：

1. 每条线两名队员的参赛 UTR 之和不超过该线 cap 加**每线** buffer 上限；
2. 各线超出量之**和**不超过该组别的**全队** buffer 额度；
3. 每对搭档的参赛 UTR 差距不超过该组别的上限；
4. 三条男双线的参赛 UTR 之和非递增（`D1 >= D2 >= D3`），相等不算违规；
5. 高 UTR 队员的**人数**与**线位**限制均不超标；
6. 十名上场队员互不重复。

系统 MUST NOT 逐线独立判定 buffer——逐线判定会放出五线各超 0.2、合计 1.0 的
非法阵容。cap、buffer 额度、差距上限与高 UTR 阈值 MUST 全部来自
`competition-rules` 的数据，MUST NOT 写成代码常量。

#### Scenario: 全部满足
- **WHEN** 校验一套五线都在 cap 内、差距合规、男双非递增、高 UTR 不超标的阵容
- **THEN** 判定为合法

#### Scenario: 单线超出但全队预算够
- **WHEN** 某条线超出 cap，且各线超出量之和仍在全队 buffer 额度内
- **THEN** 判定为合法
- **AND** 报告该线的超出量与全队 buffer 的已用量

#### Scenario: 逐线都在容差内但合计超预算
- **WHEN** 五条线各超出 0.2，全队 buffer 额度为 0.5
- **THEN** 判定为不合法，理由是全队 buffer 预算被超出，而不是任何单独一条线

#### Scenario: 男双倒挂
- **WHEN** 第二男双的参赛 UTR 之和高于第一男双
- **THEN** 判定为不合法

#### Scenario: 男双两线相等
- **WHEN** 两条男双线的参赛 UTR 之和恰好相等
- **THEN** 判定为合法——相等不是倒挂

#### Scenario: 同一名队员出现在两条线
- **WHEN** 一套阵容中某名队员同时出现在两条线上
- **THEN** 判定为不合法

#### Scenario: 违规报告指名线位与差额
- **WHEN** 校验一套不合法的阵容
- **THEN** 每一条违规都指明是哪条线、以及差了多少

### Requirement: 开放线没有上限也不消耗预算
金组的第一男双与混双是**开放线**：无 UTR 上限。系统 SHALL 把它表达为「无上限」，
MUST NOT 用一个很大的数字代替。开放线 MUST NOT 参与 cap 校验，也 MUST NOT 消耗
全队 buffer 预算。

#### Scenario: 开放线上的任意搭档都不超 cap
- **WHEN** 金组的第一男双排入一对参赛 UTR 之和很高的搭档
- **THEN** 不产生 cap 违规，也不占用 buffer 预算

#### Scenario: 开放线仍受其他约束
- **WHEN** 开放线上的一对搭档参赛 UTR 差距超过上限
- **THEN** 仍判定为不合法——开放的只是 cap

### Requirement: 高 UTR 限制同时约束人数与线位
高 UTR 队员的限制 SHALL 同时校验**人数上限**与**允许的线位**。只校验人数会放出
「把只能打第一男双或混双的队员排进第二男双」这样的非法阵容。女队员打男队员位置时，
SHALL 按男队员的限制判定。

#### Scenario: 人数超标
- **WHEN** 上场阵容中超过阈值的男队员人数超过该组别的上限
- **THEN** 判定为不合法

#### Scenario: 线位不允许
- **WHEN** 某名队员的参赛 UTR 高于只允许特定线位的阈值，却被排在其他线上
- **THEN** 判定为不合法，即便人数没有超标

#### Scenario: 女队员打男双按男队员判定
- **WHEN** 一名女队员被排在男双线上
- **THEN** 按男队员的高 UTR 限制判定她

### Requirement: 搜索在锁定与排除下补齐阵容
系统 SHALL 接受若干**锁定搭档**（指定某条线的两名队员）与若干**排除队员**
（本场不能上），在其余空间中搜出合法阵容。所有结果 MUST 包含每一对锁定搭档，
MUST NOT 包含任何被排除的队员。

#### Scenario: 无锁定无排除
- **WHEN** 不指定任何锁定与排除
- **THEN** 返回该队的合法阵容候选

#### Scenario: 锁定被遵守
- **WHEN** 锁定某条线的一对搭档后搜索
- **THEN** 每一套返回的阵容在该线上都是这对搭档

#### Scenario: 排除被遵守
- **WHEN** 排除某名队员后搜索
- **THEN** 没有任何一套返回的阵容包含该队员

#### Scenario: 锁定本身不合法
- **WHEN** 锁定的一对搭档自身就违反 cap、差距或线位约束
- **THEN** 报告该锁定不合法，而不是返回空结果

### Requirement: 候选按上场十人排序并去重
候选 SHALL 按上场十名队员的参赛 UTR 之和从高到低排序。候选 SHALL 按**上场十人的
集合**去重：同一批十人在五条线之间换位置 MUST NOT 计为两套阵容。

这个目标会顶满预算然后大面积并列——实测某些球队的最优值有数百套并列，其中一部分
只对应同一批十人。不去重的「前 N 名」会把一套阵容重排 N 遍冒充 N 个选项。

#### Scenario: 强者在前
- **WHEN** 返回多套候选
- **THEN** 按上场十人参赛 UTR 之和从高到低排列

#### Scenario: 换线不算两套
- **WHEN** 两套候选的上场十人完全相同，只是分配到不同线位
- **THEN** 结果中只出现其中一套

### Requirement: 报告可达上限与达到它的十人组合数
结果 SHALL 包含在当前锁定与排除下的**可达上限**（总和的最大值），以及**有多少组
不同的十人**能达到该上限。

只给「前 N 名」无法区分「顶点有很多种人选」与「顶点只有唯一一种人选」，而这两种
情况对排阵的意义完全不同。

#### Scenario: 上限确实是上限
- **WHEN** 完成一次未被截断的搜索
- **THEN** 没有任何一套合法阵容的总和超过报告的上限

#### Scenario: 顶点唯一
- **WHEN** 只有一组十人能达到上限
- **THEN** 报告的组合数为 1

### Requirement: 无解与截断都是显式状态
搜索无解时，系统 SHALL 报告无解，并指出**哪条线在当前锁定与排除下没有合法搭档**。
MUST NOT 用空结果列表表示无解——空列表读作「搜过了，没有找到」，与「这套限制本身
没有解」是不同的断言。

系统 MAY 一并给出该线上每名相关队员当前的去向（被锁进哪条线、或被排除），因为那是
读取当前输入即可得到的，不需要重新搜索。系统 MUST NOT 声称知道**是哪一条锁定导致
了无解**——那需要逐条去掉锁定重新搜索。

搜索 SHALL 有节点预算。触到预算时 MUST 报告结果**不完整**，MUST NOT 把截断的结果
当作完整搜索呈现。

#### Scenario: 无解指名线位
- **WHEN** 锁定与排除使得某条线没有任何合法搭档
- **THEN** 报告无解并指明是那条线
- **AND** 结果不是一个空的候选列表

#### Scenario: 截断被声明
- **WHEN** 搜索在达到节点预算时停止
- **THEN** 结果标明搜索不完整

#### Scenario: 完整搜索不谎称截断
- **WHEN** 搜索在预算内自然穷尽
- **THEN** 结果标明搜索完整

### Requirement: 外援限制不校验且明说
系统 MUST NOT 校验外援限制，并 SHALL 在结果中明确标注这一项未被校验。
每场外援上场人数的上限取决于该队由几所学校组成，而系统没有这个信息。
沉默会让人以为已经查过。

#### Scenario: 结果带有未校验声明
- **WHEN** 返回任何搜索或校验结果
- **THEN** 结果中标明外援限制未被校验

### Requirement: 提供只读的阵容搜索端点
后端 SHALL 提供一个只读端点返回搜索结果，锁定与排除通过 query 参数传入。
系统 MUST NOT 因此新增任何写方法——阵容不落库，没有东西需要写。

未知球队 SHALL 返回 404。

队员的 key SHALL 采用带前缀的形式（如 `p10531`），使**纯数字的旧格式解析失败**。
旧 key 是名单快照的主键，切换数据来源后同一个数字会指向另一个队员：两套 id 互不相干却
都是整数，恰好也存在时，页面会算出一套看着合法的阵容而锁的是两个不相干的人。因此
系统 MUST 让旧格式失败，且 MUST 说明是链接过期，MUST NOT 返回一个笼统的错误。

#### Scenario: 搜索某队的阵容
- **WHEN** 请求某支存在球队的阵容搜索
- **THEN** 返回 200 与候选、上限、以及各状态标记

#### Scenario: 未知球队
- **WHEN** 请求一支不存在的球队
- **THEN** 返回 404

#### Scenario: 锁定与排除经 query 传入
- **WHEN** 在 query 中指定锁定搭档与排除队员
- **THEN** 结果遵守它们

#### Scenario: 旧格式的 key 被拒绝
- **WHEN** query 中的锁定或排除使用纯数字的旧格式 key
- **THEN** 返回 4xx，且错误说明该链接是旧格式、队员编号已变
- **AND** MUST NOT 把这个数字当作新 key 解析

#### Scenario: 仍然不存在写方法
- **WHEN** 检查应用暴露的 HTTP 接口
- **THEN** 不存在任何指向阵容资源的 POST / PUT / PATCH / DELETE 方法

### Requirement: 参赛 UTR 的推导链
排阵取值时，一名队员该赛季的参赛 UTR SHALL 按以下顺序逐级回退，取到第一个有值的为准：

1. **该赛季的 match UTR**（冻结值）→ 来源标记 `组委会总表`
2. **当前双打 UTR**，且其状态为 `rated` → 来源标记 `估算（当前已认证值）`
3. 当前双打状态为 `projected` 或 `unrated` 时，取**最近一个有值赛季**的 match UTR
   （不限于上一年）→ 来源标记 `估算（<年份>参赛值）`
4. 都取不到 → 该队员**不参与排阵**

标记 MUST 带上年份：用 2025 的值估 2026 与用 2023 的值估 2026 是两种可信度，
标签把年份吞掉就等于把这个差别吞掉了。

这条链是组委会自己的算法（总表原则：Rated 直接用当前值，Projected 用去年的 override），
不是排阵的内部技巧，因此名单页与排阵引擎 SHALL 使用同一条链，对同一名队员给出同一个
数字。

#### Scenario: 有冻结值时不推导
- **WHEN** 队员该赛季有 match UTR
- **THEN** 取该值，来源标记为组委会总表

#### Scenario: 当前已认证的双打值优先于历史
- **WHEN** 队员该赛季无 match UTR，当前双打 UTR 状态为 `rated`
- **THEN** 取当前双打 UTR，并标记为估算

#### Scenario: 当前值不可信时回看历史
- **WHEN** 队员该赛季无 match UTR，当前双打状态为 `projected` 或 `unrated`，
  且他在更早的赛季有 match UTR
- **THEN** 取**最近**那个有值赛季的 match UTR
- **AND** 标记里写明取自哪一年

#### Scenario: 回退不限于上一年
- **WHEN** 队员 2026 与 2025 都没有 match UTR，2024 有
- **THEN** 取 2024 的值并标记为 2024 参赛值

#### Scenario: 四步都取不到
- **WHEN** 队员既无该赛季值、无当前双打值，也无任何更早赛季的值
- **THEN** 该队员不参与搜索

### Requirement: 搜索报告它没有算进去的人
搜索结果 SHALL 报出因缺少参赛 UTR 而未参与计算的队员人数。MUST NOT 静默地把人从池子
里去掉——上限与候选都建立在「参与计算的那些人」之上，不说清楚就等于让人以为这是全队
的答案。

#### Scenario: 有人未参与时说明
- **WHEN** 某支球队有 N 名队员四步都取不到参赛 UTR
- **THEN** 结果中报出 N
- **AND** 候选与可达上限均基于其余队员计算

#### Scenario: 无人缺失时不报
- **WHEN** 全队每名队员都取得到参赛 UTR
- **THEN** 未参与人数为 0

### Requirement: 估算值与未裁决值在结果中可识别
搜索结果 SHALL 标出每个参与计算的数字是冻结值、估算值，还是取自未裁决冲突的较大值。
结果 SHALL 报出**含估算值的队员人数**与**参赛 UTR 未裁决的队员人数**。

理由是合法性是**整套**的属性：五条线的和、全队 buffer、高 UTR 人数都会用到那个数字，
所以一套阵容里只要有一个估算值，「这套合法」这个结论本身就是估算。

#### Scenario: 每个数字带来源
- **WHEN** 返回任一候选阵容
- **THEN** 其中每名队员的参赛 UTR 都带有来源标记

#### Scenario: 报出两类计数
- **WHEN** 返回搜索结果
- **THEN** 结果中含估算队员数与未裁决队员数两个计数

#### Scenario: 未裁决取较大值
- **WHEN** 某名参与计算的队员该赛季的参赛 UTR 处于未裁决状态
- **THEN** 取较大的候选值参与计算
- **AND** 结果标明该队员未裁决
